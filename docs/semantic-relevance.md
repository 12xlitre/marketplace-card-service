# Подбор СЯ по содержанию карточки

Обычный подбор по кнопке «Подобрать запросы» во вкладке СЯ Wildberries и Ozon
использует card-relevance-v1. Автоматическая подготовка SEO-файлов имеет
собственный контракт. Общий подбор Ozon и постоянные фоновые задания WB/Ozon
реализованы 09.11.2026; состояние выпуска и проверки указаны в WORK.md.

## Пользовательский процесс

1. MPStats возвращает расширение стартовой фразы. Все уникальные непустые запросы
   передаются на проверку; предварительный фильтр по корням названия их не удаляет.
2. Модель проверяет каждый запрос по собственному названию, описанию и
   характеристикам. Широкий запрос или синоним может быть релевантным без дословного
   вхождения. Отсутствие существенного свойства означает спорность, противоречие —
   нерелевантность. Частота и стартовая фраза не доказывают соответствие товару.
   Число персон, общее число предметов и количество конкретных предметов различаются;
   неоднозначность запроса о части комплекта остаётся на проверку специалисту.
3. Релевантные новые запросы с прямой частотой WB/Ozon сразу включаются в подборку.
   Доступно «Исключить». Прежний лимит автодобавления 36 к этому процессу не относится.
4. Спорные запросы видны отдельно и требуют «Добавить в СЯ». Нерелевантные видны с
   причиной и не включаются. Строки без прямой частоты сохраняются для проверки,
   но не становятся новыми добавлениями.
5. Завершённый подбор автоматически сохраняется в рабочий черновик.
   «Сохранить текущий выбор» сохраняет последующие ручные изменения специалиста.
   «Добавить в итоговое СЯ» остаётся отдельным действием. Повторный подбор сохраняет
   явные включения спорных и исключения релевантных запросов.

В Ozon новые добавления требуют прямой частоты Ozon (`ozonCount`); частота WB
не заменяет её. Релевантные строки MPStats с подтверждённой частотой Ozon и
фразовым совпадением с собственным контентом показываются как действующие.
Отдельные слова из текста не создают спрос или позиции. Старые сохранённые
подборки доступны, но автоматически не переоцениваются. Решения специалиста
сохраняются и при смене стартовой фразы. «В работу» показывает также ранее
выбранные запросы, которых нет в текущем расширении.

Рабочее сохранение Ozon не меняет ранее добавленный итог. Отдельная кнопка
«Добавить в итоговое СЯ» фиксирует снимок действующих, выбранных и удаляемых
запросов; кабинетная выгрузка использует этот снимок. Перед добавлением в итог
и скачиванием файла карточки нужно сохранить текущий выбор.

Исключение нового кандидата не является предложением удалить ключ из карточки.
Для уже действующего или ранжирующегося запроса действует прежнее согласование
удаления. Старые сохранённые подборки не переоцениваются автоматически.

Назначенный руководитель проекта может менять выбор, сохранять подборку и добавлять
её в итоговое СЯ. Для этих действий используется отдельный режим доступности;
прежний запрет руководителю редактировать контент и согласовывать его сохраняется.
Во время подбора изменение выбора и сохранение заблокированы до завершения.

## Контракт API

POST `/api/semantic-jobs` с `action=start`, `portalId`, `card`, `query`, `refresh`
сначала записывает задание в SQLite и сразу возвращает `{job}`. Нужны только
идентификаторы карточки: её факты сервер читает из снимка кабинета, клиент не может
подменить их. Требуется подключённая модель; без неё MPStats не вызывается.
Необязательный `selectionState` содержит компактные `selected`, `removal`,
`decisions` (query/manualDecision), чтобы сохранить и ещё не записанный ручной выбор.
Полная история прошлых отчётов не передаётся. Каждая коллекция — до 5000 строк.
Состояние при запуске и актуальный черновик объединяются при завершении;
сохранённые параллельно решения при конфликте имеют приоритет.

GET `/api/semantic-jobs?portal_id=ID&card_key=KEY` возвращает последние задания
своего пользователя для карточки; без `card_key` — до 40 заданий кабинета.
Это только метаданные. GET с `job_id=ID` возвращает задание и готовый результат.
POST с `action=cancel|retry`, `portalId`, `jobId` отменяет или продолжает задание.
Статусы: queued, collecting, classifying, ready, failed, cancelled; saving
зарезервирован для сохранения. Метаданные включают completed/total, autoSaved,
ошибку и диапазон etaLowSeconds/etaHighSeconds после наблюдаемых порций модели.
Оценка приблизительная и не учитывает будущую очередь других заданий.

Маркетплейс определяется сервером по кабинету, а не из клиентского `card`:
для MPStats `mp=0` у Wildberries, `mp=1` у Ozon; кеши отчётов раздельные.
В Ozon запуск требует существующего права редактирования кабинета; просмотр
и опрос проверяются по прежним правилам доступа и принадлежности задания.

Ozon сохраняется через прежний POST `/api/portals/{id}/ozon-semantic-draft`:
`semanticCore` содержит полный `allKeywords`, решения/обоснования/цитаты,
источник, период, историю ручных решений `decisions`; `finalSelection` — снимок
для итоговой выгрузки. До 5000 строк вместо прежних 500, JSON до 16 МиБ,
превышение размера возвращает 413. Права сохранения прежние.

Старый POST `/api/mpstats/semantic-expansion` совместим: старт также создаёт
постоянное задание, активный ответ имеет status=classifying и phase с текущим
статусом; опрос — portalId, relevanceJobId. Опрос не обращается к MPStats
или модели. Проверяются текущая сессия, доступ к кабинету и принадлежность задания
этому пользователю/кабинету. Чужое или неизвестное задание не раскрывается.

После полной проверки возвращается прежняя структура результата с
semanticCore.relevanceVersion, relevanceCounts и всеми строками allKeywords.
Строка содержит relevance (relevant/disputed/irrelevant), relevanceReason,
relevanceEvidence (factId, quote). Фронтенд сохраняет также manualDecision
(included/excluded) в строках источника.

Каждому запросу соответствует обязательный идентификатор ответа модели.
Отсутствующее решение, повреждённый/оборванный ответ или отказ провайдера не дают
частичный результат как готовый. Неподтверждённая цитата переводит релевантное
решение в спорное. Содержательная проверка специалистом остаётся необходимой.

## Фоновые задания и кеш

SQLite-таблица `semantic_jobs` хранит вход, неизменные период/seed-фразы,
reportHash MPStats, источник, прогресс и результат. `semantic_query_cache`
хранит проверенное решение для отдельного нормализованного запроса в пределах
кабинета, пользователя, хеша собственных фактов и версии классификатора/модели.
Частота и порядок строк не меняют ключ: при повторном подборе возвращается свежая
частота с прежним проверенным решением. Смена фактов/модели требует новой проверки.
Смена исходных фактов во время задания останавливает его до оплаты новой порции
или сохранения. Доступ пользователя проверяется повторно на каждом шаге.

Один ведущий поток на БД (flock) берёт по 32 запроса из заданий по очереди;
параллельные процессы не дублируют работу. Существующая модель и глобальный
лимит параллельности сохранены. Формат ответа модели сокращён до статуса,
краткой причины и одной проверяемой цитаты; критерии релевантности прежние.
Больше 5000 уникальных запросов отклоняется явно. Общего отсечения через 30 минут
нет; отдельные HTTP-вызовы по-прежнему имеют таймауты и ограниченные повторы.
Первичный проход зависит от скорости провайдера; кеш ускоряет повторные проходы.

Прогресс каждой завершённой порции записывается атомарно. После старта сервера
воркер подхватывает незавершённые задания без браузера. Уже зафиксированные
решения не запрашиваются повторно; при аварии между внешним ответом и локальной
записью возможно повторение одной незаписанной порции. Отмена исключает позднее
сохранение черновика; ответ уже выполнявшегося вызова может быть записан в кеш,
а сам оплачиваемый HTTP-вызов отмена не отзывает.

Источник MPStats повторно используется для той же карточки в пределах срока
рыночного кеша, периода и seed-фраз. Для WB до первой модельной порции сохраняется
также ранжирование: из последнего черновика либо существующего MPStats-метода
позиций с зафиксированным периодом. Оно не зависит от открытого браузера;
ранжирующиеся запросы не становятся новыми добавлениями. Недоступность позиций
сохраняется как предупреждение источника и допускает проверку релевантности.
Создание отчёта делает одну POST-попытку; reportHash записывается до
опроса. Неопределённый исход создания останавливается с
`semantic_report_creation_unknown`, без слепого повторного платного отчёта.
Ожидание отчёта ограничено 240 опросами с паузой не менее 5 секунд;
`semantic_report_timeout` допускает продолжение того же reportHash.
Прочая ошибка требует явного «Продолжить подбор»; проверенные порции сохраняются.

Готовый результат и рабочий черновик сохраняются одной транзакцией. Сохраняются
актуальные ручные решения, ранжирование WB, другие подборки и поля контента.
Согласования, итоговый снимок и данные маркетплейса автоматически не меняются.
UI восстанавливает задание из БД при возвращении; список доступен также во вкладке
«Задачи» кабинета. Полный результат не передаётся при каждом опросе.

Ограничения очереди действуют и при продолжении: одно активное задание на карточку,
до 8 на пользователя, до 64 всего. Терминальные задания хранятся 30 дней, решения
в кеше — 90 дней; очистка при старте воркера не удаляет кеш активных заданий.
Обе таблицы имеют внешние ключи с каскадным удалением кабинета/пользователя.
Новых серверных разрешений, подключений или публикаций на маркетплейсе нет.

## Согласование в Excel

Прежние десять колонок сохранены. В конце добавлено «Обоснование добавления».
В новых добавлениях находятся оставленные релевантные и явно включённые спорные
запросы. Нерелевантные и исключённые кандидаты туда не попадают.
Колонки согласования добавления/удаления находятся в G/J; обе имеют выбор Да/Нет.
Дополнительная колонка не меняет существующий импорт согласованного файла.
Ozon использует этот же формат для файла карточки и итогового кабинетного файла.
Имя листа содержит артикул карточки, поэтому переименование самого файла
не мешает сопоставлению при загрузке в кабинет.
Обратный Ozon-импорт сохраняет обе частоты, обоснования и ручные решения, включая
«Нет» для добавления: повторный подбор не возвращает отвергнутый запрос сам.
