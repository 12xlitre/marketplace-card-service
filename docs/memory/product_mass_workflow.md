# Массовая обработка карточек

Устойчивые правила, уточнены 2026-10-20. Текущий файл, статус проверки и очередь — в [WORK.md](../../WORK.md).

## Цель и границы

Аккаунт выбирает карточки и ставит задачу специалисту; специалист готовит предложения, аккаунт проверяет пакет. Сценарий пользователя от 20.10.2026: «Взять в работу» → вид «Автоматическая оптимизация» → задача специалиста с кнопкой «Подготовить файл» → проверка и принятие либо замечания с пересборкой. После принятия специалистом — согласование аккаунтом (подтверждено пользователем). Существующие пачки и ручной контроль сохраняются. Реализация Ozon, границы пересборки, API и требования к большому Excel — в [описании процесса](../automatic-seo-workflow.md); текущая готовность/выкладка — только в WORK.md. Переписка сама приложение не изменяет.

## Источники и соответствие товару

- Сначала собственная карточка Seller API: SKU/артикул, исходные тексты, все заполненные характеристики, состав, комплект, инструкция, доступный rich-контент. Значения не додумывать.
- Семантика MPStats — за последние закрытые 30 дней. Текущая позиция — отдельный датированный срез; средняя позиция конкурента её не заменяет. `no_data` не превращать в ноль, `count` не объявлять месячными показами без подтверждения единиц и окна. Динамику видимости SKU отличать от позиции отдельного запроса.
- Для новых значений характеристик проверять официальные словари, допустимое число значений и текстовые условия категории. Существование значения в словаре не доказывает соответствия товару.
- Прямой конкурент сопоставим по назначению, конструкции, материалу, цвету и комплектации; для одежды также по рисунку/фактуре, для сантехники — по изливу, монтажу и управлению. Заданное специалистом назначение имеет приоритет. Не подставлять чужую модель, гарантию, страну или размеры.
- Явные конфликты исключать до ранжирования; неизвестное не считать совпадением, кандидатов не добирать ради количества. Оценка similarity и общая категория сами не подтверждают сопоставимость. В ревизии 19.10.2026 подбор был `manual-only-specialist-v1`; его ограничения и примеры сохранены в `var/research/competitor-selection/`.
- Датированная версия конкурента MPStats — исторический снимок, а не гарантированная текущая витрина. Ошибка локального ключа не доказывает неисправности сохранённого подключения приложения. Seller ID не подставлять вместо Client-Id без проверки доступа и идентичности магазина.

## Выбор ключей и текст

- Принцип Насти от 20.10.2026: каркас описания и ориентир выбора/количества ключей брать из описания назначенного прямого конкурента. Сначала определить, какие релевантные запросы реально употреблены у него, их уникальный набор, повторения и распределение по смысловым блокам. Не подменять этот анализ двумя вручную выбранными синонимами или списком всех запросов MPStats. Несовместимые с нашим товаром ключи исключать с объяснением; фиксированная квота количества не задана.
- Подтверждение выбора — конкретный фрагмент источника, действие и реальный фрагмент результата. Различать число формулировок перечня, повторений и независимых смысловых групп; вложенные короткие совпадения не выдавать за отдельные группы. Формулировкам из текста без наблюдения MPStats не придумывать частотность. Один анализ общего конкурента использовать повторно, но факты/исключения проверять отдельно по каждому своему SKU.
- Заголовок дополнять с сохранением смысла. Краткость сама по себе не основание для сокращения. Объяснять добавления, удаления и перестроенные исходные фразы; модель, материал, размер и комплект брать только из своих подтверждений.
- Переписывать описание по структуре/смысловым блокам конкурента, используя факты своей карточки и сохраняя её важные сведения. Формулировка Насти: «перепиши текст опираясь на структуру текста конкурента и наши текущие характеристики товара и добавь в него ключевые запросы». Чужие свойства и готовые предложения не переносить автоматически.
- После переписывания выполнять редактуру на естественный русский язык — этап, названный пользователем хьюманизатором. После него снова сверять факты и вхождения ключей: редактура не должна придумывать преимущества или терять выбранные фразы. Конкретный внешний сервис не задан. Адаптированные формы отличать от точных вхождений; неподтверждённая подпись «по смыслу» не доказывает покрытия.
- Корректные характеристики сохранять; исправления точечные. Противоречия показывать отдельно. Ограничитель температуры HWTC не равен термостату; гибкая подводка не подтверждает гибкий излив.
- Rich-контент менять только при фактической ошибке/явном противоречии. Публикация требует отдельного разрешения.
- Для Ozon 23171 пользователь требует сохранять подходящие свои теги и максимально расширять релевантными тегами/запросами прямого конкурента, удаляя точные дубли. Не сокращать до четырёх общих тегов. Проверять релевантность и у слитных форм; сохранять подходящую текущую тематику вроде #сантехника. Лимит брать из определения своей категории, не обобщать на другие площадки. Расхождение поискового наполнения с рекомендацией Ozon о тематических тегах обозначать явно.

Хештеги и общий список запросов не являются доказательством свойства товара. При написании описания использовать отдельный компактный вход: свои факты без хештегов, структуру конкурента и выбранные подтверждённые формулировки; не передавать полный чужой текст. Реальное размещение проверять после редактуры. Перепроверка сохранённого ответа не должна незаметно запускать платную генерацию.

## Excel и проверки

- Первые пять листов: «Итог», «Семантика», «Заголовки», «Характеристики», «Описания». Не добавлять «Новый текст по абзацам» и «Правки описания». Полные описания до/после — рядом на одном листе.
- В столбце добавлений к заголовку показывать поисковые фразы и полный состав новых слов/чисел по сравнению текстов: модели, единицы, служебные слова, дополнительные вхождения. Перестановка, пунктуация и регистр не являются новым словом. Удаления/смену форм показывать отдельно.
- Цвет предлагаемого значения определяется действием: оставить — зелёный, изменить/дополнить — жёлтый. Спорность источников — отдельное красное замечание и лист противоречий. Зелёный означает сохранение, а не разрешение противоречия. Изменённая ячейка имеет комментарий с прежним значением.
- Новые вхождения ключей в описании — настоящим жирным шрифтом Excel. Старые вхождения остаются обычными; пересечения объединяются. После сохранения/открытия проверять текст, позиции жирных фрагментов и список ключей. Не подменять жирный шрифт звёздочками/HTML и не выделять весь новый абзац.
- Проверять исходный порядок, отсутствие дублей/пропусков/подмены SKU, фактические значения, словари, источники ключей и честность чисел. При недоступной официальной границе не объявлять её проверенной. Число технических проверок не доказывает качество SEO.
- Проверки выполняются при сборке; признак готовности связан с хешем проверенной книги и не создаётся при провале. Отправленную версию сохранять, следующую делать отдельно. Техническая готовность не равна согласованию специалистом.
- Большая пачка: одна строка на SKU в «Итоге», ссылки к деталям, фильтры и закреплённые идентификаторы; характеристики сначала показывают правки, сохранённые значения доступны снятием фильтра. Число листов не растёт по числу товаров. Полные описания сохраняются. Решения согласования хранятся в приложении, локальные пометки Excel не синхронизируются автоматически.

## Существующие пачки и согласование

- Карточки выбираются в кабинете через «Взять в работу». Типы: СЯ, Контент, Цены, Остатки. Задачи кабинета определяются `card_drafts.meta.batch.workTypes`; сохранение обычного черновика без batch не создаёт задачу «Контент».
- Специалист проходит карточки через контекст пачки, прогресс, предыдущую/следующую, фильтры и действия «готово», «пропустить», «вернуться позже». Порядок редактируется вручную и сохраняется в `meta.batch.position`. Последовательный пакетный аудит сохраняет audit/draft, без автоматической отправки секций на согласование.
- Аккаунт проверяет сводку, принимает или возвращает. СЯ завершается явным сохранением итогового ядра; Контент/Цены/Остатки уходят из активной пачки при `submitted/approved/exported` и возвращаются при `changes_requested`.
- Отчётный период агрегирует всю пачку: частично закрыта — «В работе», полностью отправлена — «На согласовании», полностью принята/выгружена или финализирована по СЯ — «Выполнено». `batchId` связывается с `portal_work_periods.tasks_json`; Ozon допускает связи с несколькими пунктами периода и сохраняет отдельный источник данных.
- Публикация после принятия — отдельное ручное действие специалиста: WB API при подключённом encrypted token либо XLSX при отсутствии API. `approved -> exported` только после успешного ответа API или подготовки таблицы. Автоматической публикации сразу после принятия нет.
- Удаление через `POST /api/card-workset/delete-tasks` убирает batch/тип работ и matching-связь с периодом, но сохраняет результаты в `card_drafts`. История завершённых доступна в `GET /api/approval-workflow` как `completedTasks`.
- При открытии карточки из пачки сначала сопоставлять `cardKey`/`nmID`, затем непустой артикул; пустой `vendorCode` не должен выбирать первую карточку кабинета.
- Автоматический файл Ozon согласуется через API версий, обычное сохранение списка задач не меняет его статус/режим/состав. Ручная и автоматическая задачи одного SKU независимы; локальный браузерный fallback не восстанавливает автоматические задачи. Конкуренты в первой версии назначаются специалистом; уточнения карточки не меняют общую методику автоматически.
