# Backend Portals

Дата: 2026-07-30.

Решение:
- список кабинетов является backend-состоянием в SQLite `portals`;
- состав проекта хранится в `portal_members`;
- контактные данные клиента временно хранятся в `portals.client_contact_json`;
- привязка кабинета к клиенту временно хранится в `portals.client_name`; если поле пустое, frontend группирует клиента по отображаемому имени кабинета;
- frontend после логина загружает только метаданные/счётчики через `GET /api/portals?view=summary` (`realCards: []`, `cardsLoaded: false`); карточки одного открытого кабинета читает `GET /api/portals/<id>/cards` из сохранённого снимка без обращения к маркетплейсу. Проверка доступа сохраняется для обоих маршрутов. Старый полный `GET /api/portals` совместим;
- создание кабинета идет через `POST /api/portals`;
- по поручению пользователя от 29.10.2026 `anastasia.tech` может создавать WB/Ozon-кабинеты вручную и через API. Это отдельное право `user_can_create_portals`, возвращаемое как `user.canCreatePortals`; оно не расширяет управление пользователями, административные действия или доступ к чужим кабинетам. Разрешение привязано к точному логину, не к отображаемому имени. Админы/менеджеры сохраняют создание; прежняя Ozon beta-возможность проверяется отдельно для Ozon. Проверка POST выполняется до внешних вызовов. Для выбора команды Насте доступен публичный справочник активных сотрудников; доступ к их кабинетам от этого не появляется;
- в шапке клиента доступна отдельная кнопка «Добавить кабинет» для создателей; общий диалог сохраняет `clientName` открытого клиента. У Насти по умолчанию выбрана команда с ней как техспециалистом, перед сохранением её можно изменить;
- изменение состава проекта идет через `POST /api/portals/<portal_id>/team`;
- изменение имени клиента идет через `POST /api/portals/<portal_id>/client-name`; frontend уровня клиента применяет одно имя ко всем кабинетам клиента до появления отдельной backend-сущности `Client`;
- изменение контактов клиента идет через `POST /api/portals/<portal_id>/client-contact`; frontend уровня клиента применяет один контакт ко всем кабинетам клиента до появления отдельной backend-сущности `Client`;
- изменение ручного источника кабинета идет через `POST /api/portals/<portal_id>/manual-source`; маршрут доступен только для manual-кабинетов, обновляет `store_url`/`manual_source` после проверки прав и не пишет сам текст источника в admin-журнал;
- проверка Ozon-источника через MPStats идет через `POST /api/portals/<portal_id>/ozon-mpstats-probe`; маршрут доступен только пользователю с edit/manage правом на Ozon-портал, делает малый read-only probe, при наличии тестовых артикулов/SKU проверяет item-кандидаты первыми и агрегирует до 50 найденных карточек, возвращает sample-карточки и attempts, но не сохраняет карточки в `cards_snapshot_json`;
- сохранение результата Ozon probe идет отдельным `POST /api/portals/<portal_id>/ozon-mpstats-cards`; маршрут доступен только пользователю с edit/manage правом на Ozon-портал, нормализует sample-карточки как `marketplace=ozon`, мержит их в `cards_snapshot_json` по SKU/offer/id и обновляет счетчики портала без WB API/write-операций;
- Ozon beta-задачи хранятся через `GET/POST /api/portals/<portal_id>/ozon-tasks` в `ozon_tasks`/`ozon_task_events`: payload сохраняет `batchId`, `batchTitle`, `batchPosition`, `workTypes`, `workComment`, поддерживает статусы `draft/submitted/approved/done/skipped/later/returned`, а привязка к отчетному периоду идет через общий `portal_work_periods.link_task` без смешивания с WB `card_drafts`;
- рабочий набор карточек кабинета хранится в SQLite `portal_workset_cards`, читается через `GET /api/card-workset?portal_id=...` и сохраняется через `POST /api/card-workset`;
- создание массового пакета работы идет через `POST /api/card-workset/create-tasks`: backend создает внутренние `card_drafts` со статусом `draft` (`в работе`) без write-запросов в WB;
- удаление задачи идет через `POST /api/card-workset/delete-tasks`: backend очищает `meta.batch`/выбранные `workTypes` и соответствующие `approvalSections`, но не удаляет весь `card_draft`;
- безопасная очистка рабочих артефактов кабинета идет через `POST /api/portals/<portal_id>/clear-draft-work`: backend удаляет обычные черновики без `meta.batch`, а строки задач оставляет, очищая аудит/черновики контента/итоговое СЯ/переоптимизацию и возвращая секции в `draft`; `portal_workset_cards` и `card_approval_events` не удаляются;
- ручной порядок задач внутри пачки сохраняется через `POST /api/card-workset/reorder-tasks` в `card_drafts.meta.batch.position`; маршрут обязан фильтровать задачи по `portal_id` и `meta.batch.id`;
- журнал действий пачки пишется через `POST /api/card-workset/log-event`, а пакетный аудит через `POST /api/card-workset/audit-task`; оба маршрута требуют доступ к `portal_id`, работают только с существующим `card_draft` и не выполняют write-запросы в WB;
- обратная загрузка согласованного WB-СЯ идет через `POST /api/semantic-core-import`: сначала `mode=preview`, затем `mode=apply`; маршрут читает XLSX/CSV/TXT, сопоставляет карточки по `cardKey`/`nmID`/артикулу/листу или категорийным файлам и обновляет только `card_drafts.meta.semanticCoreFinal`, `semanticCoreSelected`, `semanticCoreRemoval` без write-запросов в WB;
- публикация принятого WB-контента идет через `POST /api/portals/<portal_id>/wb-content-publication`: маршрут требует техспециалиста проекта или админа, проверяет `marketplace=Wildberries`, берет только approved/exported секцию `Контент`, в `mode=api` отправляет WB `POST /content/v2/cards/update`, а в `mode=table` возвращает данные для XLSX и помечает контент как `exported`;
- `approval_workflow` отдает по задачам `auditStatus` и `hasAuditDraft`; frontend пакетного аудита использует это, чтобы после частичного запуска продолжать только карточки без сохраненного audit draft, а локальные ошибки повторять отдельным failed-списком;
- для ошибок пакетного аудита `card_approval_events.action` может быть `audit_failed`, а backend возвращает безопасный код `audit_task_failed` + тип исключения без stack trace и без секретов;
- `localStorage` в frontend остается только временным fallback, когда backend еще недоступен на контуре.

Правила:
- Если сохранённый в браузере ID клиента/кабинета больше не существует или недоступен, возвращаться к списку клиентов. Не подставлять первый доступный кабинет/клиента вместо явно сохранённого удалённого ID: это открывает чужой рабочий контекст и выглядит как самопроизвольный возврат старого кабинета.
- По уточнению пользователя 29.10.2026 Кристина Январева (`kristina.manager`, роль «Руководитель отдела») видит всех клиентов и все WB/Ozon-кабинеты независимо от назначения в команду, включая архив через общий фильтр. Серверный глобальный доступ руководителя уже предусмотрен; интерфейс и серверная Ozon beta-проверка обязаны учитывать эту роль. Обзор руководителя не ограничивать правилами техспециалиста/аккаунт-менеджера; совпадение имени с Кристиной без роли само по себе прав не даёт.
- WB API токены не попадают в ответ `GET /api/portals`;
- контактные данные клиента возвращаются как `clientContact` и не пишутся в admin-журнал целиком: событие фиксирует только заполненные типы полей;
- изменение `clientName` в admin-журнале фиксирует факт изменения, но не пишет старое/новое имя клиента целиком;
- `clientName` не является полноценной сущностью клиента и нужен только для текущей группировки нескольких marketplace-кабинетов; если имя не задано и кабинет называется технически (`Кабинет WB`/`WB`), frontend показывает клиента как `Клиент без названия`, чтобы его можно было явно переименовать;
- архивирование/удаление клиента во frontend пока является массовым действием по кабинетам клиента: архив отправляет в архив все активные кабинеты, удаление доступно только после архива и вызывает удаление каждого архивного кабинета;
- `portal_integrations.external_key` хранит не секретный fingerprint внешнего кабинета/набора карточек для защиты от повторного добавления;
- счетчики `card_count`, `work_count`, `problem_count` и `last_sync_at` обновляются после read-only загрузки WB;
- карточки пока не являются отдельной постоянной таблицей; открытие кабинета читает сохранённый snapshot. Только явное обновление WB использует `/api/wb/cards`; выбранный состав сохраняется при обновлении и замене ключа.
