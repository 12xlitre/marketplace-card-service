# Карточки из Ozon Seller API

Дата: 2026-10-19.

## Premortem

Решение: загружать карточки из сохранённого Seller API этого Ozon-кабинета при API-создании и по явному обновлению, сохраняя существующие задачи и черновики.

Вердикт: GO с условиями — сначала проверить форматы реального read API, затем реализовать получение и атомарное сохранение. Никаких write-методов маркетплейса.

## Источники контрактов

Рабочие BOSF-снимки `product/list`, `product/info/list` и `product/info/attributes` из сохранённой папки Даши. Официальная https://docs.ozon.ru/api/seller/ при проверке 2026-10-19 недоступна из-за redirect loop; методы и структуру дополнительно проверяем прямыми read-запросами с уже сохранённым доступом HoneyBear без вывода ключей.


## Контракт и интерфейс

`POST /api/portals/<id>/ozon-seller-cards`: сессия, edit-доступ и marketplace Ozon проверяются до чтения ключа и сети. Тело пустое; доступ берётся только из encrypted `portal_integrations` provider `ozon` с AAD кабинета. Возвращает `portal`, `saved` (added/updated/total/loadedAt), `productCount` магазина.

`POST /api/portals` с `mode=api`, `marketplace=Ozon` теперь загружает карточки до создания. Кабинет, команда, ключ и карточки сохраняются одной транзакцией; неудача не оставляет пустой кабинет. Сохранение доступа существующего кабинета через форму запускает загрузку отдельным запросом.

В публичной модели добавлен `ozonApiConnected`; `mode=api` учитывает Ozon-подключение. Legacy `api_connected` / `apiConnected` остаются в WB-контуре, чтобы общие эффекты не запускали `/api/wb/cards` для Ozon. Для Ozon с доступом главная кнопка и действие в настройках используют Seller API даже без ссылки/Seller ID. MPStats остаётся ручным источником для кабинетов без Seller API и отдельным источником семантики.

Методы чтения: `/v3/product/list` (visibility ALL, cursor last_id, до 1000 на страницу), `/v3/product/info/list` и `/v4/product/info/attributes` (пачки по 100 ID), `/v1/description-category/attribute` (один раз на category/type в загрузке). Product ID, SKU и offer ID сохраняются отдельно. Описание берётся из атрибута 4191, бренд из 85, названия характеристик из справочника; исходные значения и dictionary IDs сохранены в rawFields. В реальном API complex_attributes — плоские строки с id/complex_id/values; поддержаны также вложенные группы attributes.

Общее время — 45 секунд; connect до 5 секунд, чтение до 15 секунд с учётом оставшегося общего времени, чтение порциями с проверкой времени и размера. Максимум 8 MiB на ответ, 32 MiB на итоговый snapshot и 2000 товаров магазина. При превышении — явная ошибка, без скрытого обрезания. Для более крупных магазинов потребуется фоновая загрузка. Retry — три попытки только для сети, 429 и выбранных 5xx, backoff 0.5/1s, Retry-After; ожидание больше 5 секунд возвращает управление пользователю. Нет redirect и произвольного URL/метода. Повторный sync ограничен 10 секундами на кабинет; in-flight общий с проверкой подключения. Проверка ключа и sync имеют отдельные интервалы, поэтому сохранение ключа не мешает первой загрузке.

При неполном списке/дубликате cursor/недостающих ID в info/attributes snapshot не записывается. Selected-режим разрешает SKU/product ID/offer ID только из текущего API-аккаунта и требует найти весь список. Данные сливаются по product ID/SKU/offer ID, прежние id/cardKey сохраняются. Не вернувшиеся карточки не удаляются. Задачи, СЯ, согласования и черновики не затрагиваются. Неоднозначные идентификаторы блокируют запись. Перед сохранением проверяются версия ключа, scope и исходный список. Цена и остаток берутся из info, нулевой остаток сохраняется как 0; неизвестные продажи/выручка/отзывы не выдумываются.

Безопасные ошибки: `ozon_connection_required`, `ozon_auth_error`, `ozon_check_rate_limited`, `ozon_sync_timeout`, `ozon_sync_limit`, `ozon_response_too_large`, `ozon_incomplete_response`, `ozon_selected_cards_not_found`, `ozon_card_identity_conflict`, `ozon_connection_changed`. UI объясняет их без перенаправления API-кабинета к MPStats. Все ошибки сохраняют прежние карточки.
