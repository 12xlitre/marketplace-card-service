# Автоматическая оптимизация карточек

Первая версия автоматической оптимизации Ozon от 20 октября 2026 года; с 29 октября тот же процесс реализован для Wildberries. Аккаунт выбирает карточки, специалист запускает подготовку Excel, проверяет результат и принимает версию либо задаёт замечания для пересборки. После принятия специалистом файл передаётся аккаунту на согласование. Публикация карточек на маркетплейсе остаётся отдельным действием.

## Wildberries и план работ — 29.10.2026

В WB окно «Взять в работу» предлагает ручную работу и автоматическую оптимизацию. Для автоматической нужен подключённый WB API кабинета; после выбора карточек задача появляется отдельно во вкладке «Задачи». Специалист указывает конкурента числовым nmID либо полным адресом `wildberries.ru/catalog/<nmID>/detail.aspx`, запускает файл и получает те же восемь листов, версии, замечания и согласование, что в Ozon. В книге WB идентификатор подписан nmID. Старые ручные WB-черновики не заменяются автоматической задачей для того же товара.

WB-автозадачи хранятся в новой таблице `automatic_seo_tasks`, с FK на свой portal_id, batch_id, неизменяемым составом, отдельным статусом и payload; Ozon продолжает использовать `ozon_tasks`. `POST /api/card-workset/create-tasks` принимает `optimizationMode: automatic`; общая выдача/удаление WB-автозадач — `GET/POST /api/portals/<id>/automatic-seo-tasks` (POST: action=delete, batchId). Файл и решения по обеим площадкам используют прежний `/automatic-seo/<batch>`; выбор адаптера определяется маркетплейсом кабинета на сервере, не параметром клиента. Создание — менеджер с доступом или назначенный техспециалист; подготовка и принятие — назначенный техспециалист/администратор, согласование — назначенный аккаунт/администратор. До 200 карточек в пачке, до 500 активных WB-автозадач; повторная активная автозадача для того же nmID отклоняется. Управленческий обзор считает автозадачи вместе с обычными задачами.

Собственные данные WB получает существующий read-клиент Content API по encrypted-токену конкретного кабинета; справочник предмета — `/content/v2/object/charcs/<subjectID>`, тип/число значений и directory valueOptions проверяются в WB-адаптере. Ozon-ID/правила хештегов к WB не применяются. Название проверяется по пределу 60 символов ([официальная документация WB](https://dev.wildberries.cn/docs/openapi/item-management)); описание имеет рабочий верхний предел 5000 с явным замечанием о категорийном ограничении, которое требует проверки перед переносом. Если выбранный nmID не покрыт полученным API-снимком, файл не выдаётся как полный. Конкурент и версии описания — прежние WB full_page-методы MPStats; семантика — постраничный WB keywords POST, до 10000 строк с явным отказом при превышении вместо молчаливого усечения. Средние позиции периода не подменяют датированные позиции: граничные дни читаются отдельно. WB search_visibility не выдумывается при отсутствии источника.

Для Ozon создание задачи с планом теперь выполняется одним POST `/ozon-tasks`: `linkBatchId` и `workPeriodLinks: [{periodId, taskKey}]`. Сами задачи и привязки записываются одной SQLite-транзакцией; неверный/исключённый/архивный/чужой пункт откатывает создание. WB-автозадачи используют тот же транзакционный helper. Неуспешная серверная подготовка новой Ozon-задачи не попадает в локальный fallback как якобы созданная. При отдельном редактировании связей ошибка оставляет диалог и выбор открытыми. Агрегация плана различает WB-черновики, WB-автозадачи и Ozon-задачи; статусы пачки синхронизируются при переходах и чтении плана, а удаление задачи очищает matching-связи. Развёртывание требует резервной копии SQLite перед первым запуском с новой таблицей; новых Python-модулей для COPY не добавлено.

Контрольный пример методики — редакция 3 Ideal Standard / AM.PM, получившая положительную оценку Насти. Текущий статус разработки и ссылки на файлы — в [WORK.md](../WORK.md). Методика источников, выбора ключей и проверки фактов — в [правилах массовой обработки](memory/product_mass_workflow.md).

## Создание задачи

В существующем окне «Взять в работу» появляется вариант «Автоматическая оптимизация». Аккаунт выбирает SKU, название задачи, специалиста в рамках существующего назначения, пункт отчётного периода и при необходимости комментарий/магазин конкурента. Порядок и состав карточек фиксируются при создании.

Внутренняя модель: задача «Контент» с `optimizationMode: automatic` в метаданных. Это отдельный вид работы в интерфейсе; он использует существующий маршрут согласования контента. Не требуется одновременно ставить отдельную задачу СЯ: получение необходимой семантики входит в подготовку файла. Ручная и автоматическая задачи могут существовать для одного SKU независимо. Предел автоматической пачки — 200 SKU, всего в кабинете — 500 задач; превышение не приводит к молчаливому усечению списка.

Рядом с каждым нашим товаром показано поле конкурента: специалист вставляет полный адрес карточки Ozon или SKU. Повторно вводить наш SKU и писать объяснение сопоставимости не требуется. SKU извлекается из ссылки на сервере без переходов по внешним адресам; принимаются только карточки домена Ozon. Для короткой ссылки нужен полный адрес открытой карточки. Назначения сохраняются между версиями; общий магазин не запускает универсальный автоматический подбор. Модель проверяет назначение, конструкцию, материал, монтаж/размер и комплектацию; явная несовместимость блокирует принятие. Отсутствие данных не считается совпадением.

## Задача специалиста

Внутри задачи: состав пачки, источники/дата данных, назначенные конкуренты, кнопка «Подготовить файл», прогресс по этапам и SKU. Для отсутствующих сопоставлений специалист назначает конкурентов до генерации соответствующих карточек.

Подготовка выполняется фоновой задачей сервера и продолжается после закрытия страницы. Повторное нажатие не создаёт параллельную копию той же работы. Одновременно выполняются до двух генераций на процесс сервера; при занятой ёмкости новый запуск отклоняется до обращения к API. Прогресс показывает подготовленные, требующие уточнения и неудавшиеся SKU; ошибочные повторяются без повторной генерации успешных, замечания не теряются. Если промежуточная попытка не дала результата, для полей вне замечания берётся последний проверяемый результат с тем же снимком источников, составом и конкурентом. При частичной ошибке Excel не создаётся: интерфейс явно показывает это рядом с версией и объясняет ошибки. Номер попытки не означает наличие файла. Для готовой версии кнопка скачивания загружает Excel без перехода на страницу API; ошибки доступа/целостности показываются в задаче. После перезапуска сервера прерванный запуск можно продолжить с сохранённых результатов вручную.

После подготовки доступны:

- «Скачать файл» с номером версии и датой;
- «Принять файл» — принять проверенную версию и передать её аккаунту;
- «Пересобрать по замечанию» — указать область и запустить доработку;
- история файлов, замечаний и решений.

Принятие привязано к определённой версии файла, а не к последней версии по имени. При пересборке новая версия требует новой проверки. Неполный охват SKU, ошибка проверки книги или нерешённое противоречие, влияющее на предлагаемые факты, блокируют принятие соответствующего результата. Замечание к источнику, которое не мешает нейтральному подтверждённому тексту, можно оставить с явным решением специалиста и обоснованием.

## Замечания и повторная подготовка

Форма содержит SKU или «Вся пачка», раздел «Заголовок / Характеристики / Описание / Семантика / Конкурент», при необходимости ID характеристики и текст замечания с указанием подтверждения факта. Первая форма отправляет одно замечание за запуск; API поддерживает список до 100 замечаний. Внешние документы/фотографии как новые доказательства и импорт пометок из Excel не реализованы. Для смены конкурента редактируется сопоставление перед пересборкой. Произвольные изменения оформления Excel выполняются доработкой экспортёра, не интерпретируются из замечания к товару.

Пример: `5318018800 → Описание → не использовать спорную серию; остальные свойства сохранить`. Для фактического исправления цвета или гарантии нужен источник: свободный комментарий не становится автоматически достоверной характеристикой.

Пересборка повторно использует зафиксированные данные и анализ общего конкурента. Изменяет только затронутые SKU и разделы; заново проверяет связанные ключи, характеристики, счётчики и противоречия. Например, смена конкурента требует пересмотреть семантику и текстовые предложения данного SKU. Изменение общего правила затрагивает все SKU, к которым оно относится: область воздействия показывается перед запуском.

Незатронутые результаты сохраняются в новой версии. После замечаний аккаунта они возвращаются специалисту в ту же задачу и проходят этот же цикл. Предыдущие файлы и решения не перезаписываются. Уточнение конкретной карточки не меняет общую методику без явного отдельного решения.

Данные не обновляются молча между редакциями. Для обновления источников предусмотрено отдельное действие с датой и показом затронутых товаров; это может потребовать перепроверки ранее принятого текста.

## Excel для большой пачки

Количество листов не растёт с числом SKU. Первые пять сохраняются: «Итог», «Семантика», «Заголовки», «Характеристики», «Описания». Далее — источники и вопросы; короткая инструкция доступна отдельно. Не делать отдельный лист на каждый товар и не возвращать удалённые листы разбивки описания по абзацам/ключам.

| Лист | Организация просмотра |
| --- | --- |
| Итог | Одна компактная строка на SKU: артикул, товар, приоритет, число правок и вопросов, статус проверки. Ссылки на строки заголовка, характеристик, описания и вопросов. Фильтры и закреплённые идентификаторы. Длинные пояснения свёрнуты по умолчанию. |
| Заголовки | До/после рядом; полные добавления, удаления и обоснования сохранены. Фильтр по SKU. |
| Характеристики | По умолчанию фильтр показывает только предлагаемые правки. Все исходные корректные значения остаются в книге и доступны при снятии фильтра. |
| Описания | Полные тексты до/после рядом, новые ключи жирным. Без сокращения текста ради компактности; переход из «Итога» сразу к нужному SKU. |
| Семантика | Полный набор с решением, источником и подтверждением использования. Фильтры SKU, релевантности, назначения и решения. Число запросов не становится обязательным числом вставок. |
| Противоречия | SKU, поле, расхождение, действие/вопрос, источник. В рабочей версии приложения также решение и состояние вопроса. |
| Изменения версии | Для повторных генераций: SKU, поле, прежнее предложение, новое предложение, замечание и причина. Это сравнение версий, а не дополнительная разбивка описания. |

У книги — номер версии, дата данных, общий охват и число успешных/проблемных карточек. Подсчёт правок идёт по реальным отличиям: заголовок, каждое изменённое поле характеристики и описание; счётчики на главном листе сверяются с деталями. Поля API, дублирующие название и аннотацию, учитываются по одному разу в профильных разделах, а не повторно как дополнительные характеристики. Общие вопросы по источникам показываются отдельно от вопросов конкретных SKU. Исходный порядок SKU сохраняется; приоритет доступен как фильтр/сортировка, не как молчаливое изменение порядка.

Статусы и решения в приложении — источник согласования. Выпадающий список и комментарии в Excel допустимы как локальные пометки, но файл не должен обещать их автоматическую синхронизацию. Импорт отредактированного Excel в первую версию не входит; замечания специалист вводит через форму задачи.

Макет на пяти реальных SKU проверяет компоновку и сохранность содержимого принятого образца. Автотест экспорта проходит на 5, 50 и 200 искусственных SKU: охват/порядок, фиксированное число листов, текст и жирное выделение, безопасное сохранение строк и отсутствие выдуманных метрик. Это проверка экспортёра, не замер скорости всей генерации или оценка SEO сотен реальных товаров. Качество реальной генерации проверяется специалистом при запуске из приложения.

## Ресурсы и данные

Общие этапы выполняются один раз на запуск/источник: словарь категории, получение общей семантики и анализ одного и того же конкурента. Собственные факты и допустимость ключей проверяются отдельно по SKU. На доработке не отправляется вся история переписки и весь отчёт модели: только правила, затронутые факты, выбранный конкурент и конкретные замечания.

При разборе формулировок конкурента проверяются заголовок и описание. Проверка допускает разницу регистра, пробелов и е/ё и сохраняет фактическое написание из источника. Для ключа, прерванного короткой буквенной вставкой в скобках в заголовке, сохраняются полный исходный заголовок и признак сопоставления без вставки; это не точная цитата непрерывной фразы. Релевантные MPStats-запросы, найденные в заголовке, включаются в обязательный перечень решений независимо от извлечения моделью. Не найденные в источнике кандидаты исключаются с явным замечанием; если ни одна предложенная формулировка не подтверждена, подготовка останавливается. Чужие свойства не переносятся автоматически.

Методика `competitor-title-description-v2` (29.10.2026): все выбранные для описания формулировки передаются писателю, включая дополнительные семантические кандидаты. После генерации релевантные запросы без точного вхождения проверяются отдельными партиями до 24: либо подтверждённая адаптация/объединение с цитатой готового поля и объяснением связи, либо конкретная причина пропуска. Список с одной только оценкой «релевантен» не считается объяснением. При отсутствии проверяемого решения в Excel показывается «требует решения» и блокирующий вопрос. Причина/адаптация кэшируется по фактам, запросам и финальным текстам. При изменении принятых характеристик применение проверяется повторно. Offline recheck не вызывает модель для отсутствующего в старом снимке ответа, а оставляет нерешённый вопрос. Дополнительные проверки могут увеличивать число модельных вызовов обычной подготовки, но не выполняются для уже покрытых точным вхождением запросов.

План модели передаёт дополнительные выбранные запросы в `additionalKeywords` с ограничением источника релевантными кандидатами; неподтверждённый источник отклоняется до вызова писателя. В Excel «Источник» сохраняет MPStats/count SKU и добавляет поле/цитату конкурента. Старый успешный результат не переиспользуется обычным запуском под новой методикой без генерации; существующие файлы сохраняются. Замечание только к заголовку/характеристике сохраняет незатронутое описание и его прежний перечень формулировок.

Запуск сохраняет версию методики, снимки источников, выбранные сопоставления, результаты по SKU, замечания, файл и его хеш. Доступ к задаче, источникам и скачиванию проверяется по кабинету и текущему пользователю. Ключи кабинетов не входят в файл, запросы генерации или журналы. Принятие старой версии во время пересборки должно возвращать понятный конфликт версий.

## Код и эксплуатация

- `automatic_seo.py` — фоновая работа, сохранение версий, ограниченная пересборка, проверка текстовых вхождений, состояния и приёмка. Редактура выполняется моделью внутри структурированного ответа с исходным черновиком и финальным текстом; внешний хьюманизатор не подключён.
- `automatic_seo_host.py` — существующие права, собственные данные Seller API, версии/запросы MPStats и проверка значений по официальным словарям. До первого запуска проверяются подключения без сетевых запросов.
- `automatic_seo_xlsx.py` — Excel с навигацией, фильтрами, цветами, прежними значениями в комментариях, полными текстами и сравнением версий; после сохранения проверяются охват, счётчики, текст/жирный шрифт и отсутствие формул из внешних строк.
- `frontend/src/AutomaticSeoTask.jsx` — экран специалиста/аккаунта; ручные кнопки изменения статуса скрыты для автоматических задач. Назначенный `tech` готовит/принимает, назначенный `manager` согласует/возвращает; администратор может оба действия. Действующие ограничения доступа к Ozon сохраняются.
- `server.py` — маршруты, метка задачи и миграция уникальности `ozon_tasks`. Миграция сохраняет поля, ID, историю и счётчик ID; уникальность `(portal_id, task_id)` остаётся, прежний запрет нескольких задач на карточку снят. Повторный запуск миграции безопасен. Другие таблицы и ручные результаты не меняются.

Данные — в `<каталог SQLite>/automatic-seo/<portal_id>/<хеш batch_id>/`: `state.json` с источниками/результатами, компактный `metadata.json` для опроса прогресса и неизменяемые `seo-vN.xlsx`. Каталоги создаются с правами 700, файлы состояния/отчётов — 600; доступ идёт через проверяемый API. Файловые блокировки защищают состояние и повторный запуск. При опросе прогресса не загружается весь набор источников. Каталог входит в резервную копию `var` вместе с SQLite.

Удаление кабинета удаляет его каталог отчётов, включая источники и все версии. Воркер перепроверяет кабинет/задачу до сохранения; после удаления он не восстанавливает файлы. Это проверено тестом удаления во время незавершённой подготовки с сохранением данных другого кабинета. Срок хранения истории согласования требует отдельного решения; автоматическое удаление принятых версий не включено.

Автоматические задачи не восстанавливаются из localStorage. Устаревшее сохранение списка задач не может согласовать файл, сменить его режим/состав или восстановить ранее удалённую автоматическую задачу. Обновление источников — явная кнопка «Обновить источники и пересобрать всё»; она повторно обрабатывает всю пачку и создаёт следующую версию.

## API

Базовый путь: `/api/portals/{portal_id}/automatic-seo/{batch_id}`.

| Метод | Действие |
| --- | --- |
| GET | Версии, состояние/прогресс, вопросы, назначения конкурентов и доступные действия текущему пользователю. Сырые источники и ключи не возвращаются. |
| POST | `action`: `generate`, `revise`, `accept`, `approve`, `return`; `version` — ожидаемый номер, сначала 0. Несовпадение или повтор активного запуска — 409. |
| GET `.../file?version=N` | Конкретный проверенный Excel после проверки кабинета, состава задачи и хеша. Частичная/непроверенная версия недоступна. |

Для подготовки: `competitors: {"свой SKU": {"sku": "SKU или полный адрес карточки конкурента"}}`; необязательное поле `reason` сохраняет совместимость с прежними версиями; для доработки/возврата — `remarks: [{sku: "SKU или *", section, text, attributeId?}]`; для принятия вопросов к источникам — `acknowledgeIssues: true`. `refreshSources: true` на подготовке явно обновляет все источники. Принятие с блокирующими вопросами запрещено. Переходы: `running → review/partial/failed`, `review → submitted` специалистом, `submitted → approved/returned` аккаунтом; прерванный запуск определяется как `interrupted`.

## Формат ответа модели

Описание возвращается отдельным вызовом обычным текстом, без JSON и function_call. Писатель получает собственные факты без хештегов, выбранные подтверждённые формулировки и структуру конкурента; полный чужой текст и общий список запросов не передаются. Markdown удаляется. Потерянное числовое условие восстанавливается целым исходным предложением, с объяснением в комментарии к описанию; новые факты при этом не сочиняются. В плане запрашиваются только разделы текущего замечания. Релевантность использует фактическую проекцию без хештегов и кэш версии v3; результаты старой оценки по сырым атрибутам не подменяют новую проверку. Приватный журнал сохраняет счётчики использования модели, если их вернул API.

Для автоматической оптимизации GigaChat получает схемы анализа конкурента, оценки релевантности, короткого плана правок. На действующем v1-адресе используется принудительный `function_call: {name: "prepare_seo_data"}` с единственной описанной функцией; читается объект `message.function_call.arguments`. Если API вернул обычный JSON-текст, он проходит тот же строгий разбор/валидацию; отсутствие native-обёртки не означает автоматически повреждение данных. Устаревший ответ очищается перед новым вызовом, новый снимок содержит время получения. Функция только описывает возвращаемые данные и не выполняет внешних действий. Контракт сверён с [официальной документацией GigaChat](https://developers.sber.ru/docs/ru/gigachat/guides/functions/generating-arguments-for-custom-functions). Обязательные поля/типы/перечисления передаются в API. Для каждой фразы конкурента создаётся обязательное решение k0/k1/…; исходную формулировку восстанавливает сервер. ID характеристик ограничены официальными определениями категории, технические заголовок/аннотация/rich исключены; неизменённые значения модели не становятся правками. Параметр response_format на фактическом окружении не обеспечил формат: это проверено живым запросом; поэтому одной инструкции «JSON» недостаточно. Прежние вызовы других функций приложения без схемы сохраняют свои параметры. Схема не заменяет проверку релевантности, фактов, словарей и полноты семантики.

Проверка релевантности разделена на порции до 32 запросов: каждая получает собственные факты товара и возвращает короткое решение по каждому запросу. Запросам назначаются идентификаторы q0/q1/…; каждый идентификатор — обязательное поле схемы, а текст запроса сопоставляется на сервере, исключая ошибки переписывания. Пропуски показываются конкретным списком. Это размер технического запроса, не квота добавляемых ключей. Проверенные порции сохраняются по хешу фактов/состава и используются повторно. Затем короткий вызов составляет план заголовка/характеристик и выбора ключей; отдельный вызов пишет только описание по собственным фактам, структуре и выбранным формулировкам. Полный текст конкурента на этапе написания не передаётся. Из rich в модель передаётся извлечённый текст, исходные JSON/медиа остаются в снимке без изменений. Фактическое размещение определяет приложение по точным вхождениям в итоговых полях и явно подтверждённым адаптациям; модель больше не возвращает огромную таблицу semanticDecisions вместе с текстом. Неразмещённые решения объединяются с полной оценкой релевантности, поэтому все исходные запросы остаются в Excel. Лимит времени проверяется между порциями, общий прогресс показывает их номера.

Предложение характеристики без подтверждающей цитаты исключается из правок: существующее значение остаётся, а предлагаемое значение и причина отказа попадают в блокирующий вопрос. Это позволяет скачать полный файл для проверки без принятия неподтверждённой правки. Предложение, не прошедшее проверку официального словаря/лимита/дублей, также исключается с замечанием. Если непринятое значение осталось в заголовке/описании, замечание блокирует принятие; исключённый кандидат без оставшегося утверждения не превращается в принятую правку. Выбранная обязательная формулировка конкурента без фактического вхождения выносится в блокирующий вопрос. Дополнительные кандидаты MPStats не обязаны все попасть в текст; их использование определяется по реальным вхождениям. Новые подтверждённые вхождения синхронизируются с перечнем ключей и жирным выделением. Литералы \n\n декодируются в абзацы; дефис между теми же словами считается допустимым написанием, свидетельство сохраняется из настоящего текста.

Неточное имя источника восстанавливается только по реально найденной цитате в собственных данных данного товара; данные конкурента для этого не используются. Принятие при блокирующих вопросах остаётся запрещённым.

## Диагностика ошибок подготовки

Ошибки модели различают таймаут, сетевой сбой, HTTP-отказ, обрыв ответа по длине, некорректный JSON и неверную структуру. Для неподтверждённых фраз сохраняется конкретный список. Публичная ошибка содержит безопасный код, этап и контролируемые детали; тексты HTTP-ошибок и секреты не передаются. Журнал сервера фиксирует SKU, кабинет, версию, класс исключения и места вызовов без сообщений исключений, переменных и тел запросов/ответов. Ответы модели сохраняются только в приватном снимке задачи для воспроизведения, до проверки содержимого; metadata и скачиваемый файл не включают этот журнал. Общие проверки доступа и удаления кабинета сохраняются. В обычной генерации повреждённый JSON, отсутствующие/некорректные аргументы функции или оборванный по длине ответ повторяются не более одного раза на том же этапе (максимум два вызова); каждый ответ сохраняется в приватном журнале до проверки структуры. Отказ модели не повторяется. Повторных вызовов модели по диагностике/recheck автоматически не выполняется. Служебное действие `recheck` доступно тем же ролям подготовки для неудачной/прерванной попытки либо файла на проверке с блокирующими замечаниями: оно заново проверяет сохранённые ответы без вызовов модели и MPStats, с запретом смены источников/конкурентов/замечаний. Если снимка не хватает, повторная генерация не запускается. Проверка официального словаря Seller API остаётся разрешённой. Обычная доработка по замечанию генерирует новый ответ, этот режим ей не подменяет результат.

Вердикт premortem: GO с условиями — область пересборки, версии, проверка полноты и изоляция файлов входят в первую реализацию.

Contrarian: сильнейшие возражения к сценарию:

- Удобная кнопка не делает автоматическим подбор прямого конкурента. Без достаточных данных нужен явный выбор специалиста; подмена сопоставления общей категорией неприемлема.
- Excel со ссылками ускоряет просмотр, но не гарантирует внимательную проверку 200 товаров. Приёмка должна явно показывать остаток непроверенных/проблемных результатов и не маскировать их общим зелёным статусом.
- Перегенерация по свободному тексту может давать бесконечные новые варианты без исправления причины. Нужны ограниченная область, источник факта и сравнение с предыдущим предложением.
- Открытый Excel не сообщает приложению, что специалист его прочитал или исправил. Нельзя автоматически принимать локальные отметки за решение в системе.
- Новый глобальный тип работ затронет много существующих правил завершения. В первой версии дешевле использовать режим задачи «Контент» с явной меткой «Автоматическая оптимизация» в интерфейсе.

Вердикт критика: начинать с Ozon, существующих пачек и файла для ручной проверки; не обещать публикацию, универсальный автоподбор или одинаково качественный результат во всех категориях. Расширение на WB требует проверки его источников, словарей и ограничений отдельно.

## Порядок внедрения

1. Режим задачи, экран специалиста, фоновый запуск и версия файла без изменения ручного процесса.
2. Перенос методики редакции 3 в сервис генерации с повторным использованием источников и новым экспортом Excel.
3. Замечания, ограниченная пересборка, сравнение версий, принятие специалистом и существующее согласование аккаунтом.
4. Проверка на пяти контрольных SKU и больших тестовых пачках; проверка сохранности ручных задач, отказов источников, версий, доступа и отсутствия автоматической публикации.

Готовность окружения и результаты выкладки записаны в `WORK.md`. Положительная оценка контрольного файла не заменяет содержательную проверку первого автоматически полученного отчёта.

Вердикт premortem: GO с проверкой на живом примере, сохранением фактов и закрытым доступом. Критика contrarian: структура и сами ключи тоже могут переносить чужие свойства; собственные источники могут противоречить; два этапа не заменяют человеческую проверку; старые снимки нельзя выдавать за новую генерацию; дополнительные вызовы могут увеличить стоимость. Красные линии: не считать непроверенные вхождения реальными, не переносить полный чужой текст на этап написания, не менять тариф без отдельного решения. ## Прогресс и уведомления — 29.10.2026

Интерфейс показывает две независимые шкалы: фактически обработанные карточки пачки и проверку запросов текущей карточки. Диапазон `161–192 из 245` означает, что проверяются эти запросы, а завершены предыдущие 160; это не 192 завершённых запроса и не прогресс всей пачки. При сборке Excel шкала ограничена 99%; готовность файла — только после сохранённого проверенного SHA256. Частичный/ошибочный результат не подписывается готовым файлом. Показывается прошедшее время, диапазон оставшегося времени появляется после двух обработанных карточек и уточняется по наблюдаемой скорости. Это приблизительная оценка, а не срок. Компонент `SeoGenerationProgress.jsx`, расчёт `seoProgress.js`; история версий и согласование прежние. Сбой GET наблюдения повторяется через10с, штатный polling3с; уход со страницы не отменяет серверную работу.

Для Битрикс24 пользователь указал `weboptimize.bitrix24.ru`, профиль Насти91. Сервер сопоставляет только точный логин `anastasia.tech` с ID91 и отправляет уведомление только по кабинетам, где она активна и назначена tech. Настройка доступна только администратору в «Администрирование → Интеграции». `GET/POST /api/integrations/bitrix-notifications`; POST `{webhook}` проверяет URL и read-only `scope` (обязателен `im`), затем шифрует вебхук в `service_integrations`, provider `bitrix-notifications`, AAD собственного provider. POST `{action: disconnect}` отключает и отменяет pending-уведомления. В ответах/логах и frontend-сборке секрета нет. Разрешён только HTTPS указанного портала и webhook-path, без redirects/произвольных URL.

После сохранения окончательного SEO-результата создаётся outbox `var/automatic-seo/<portal>/<batch-hash>/bitrix-notification-vN.json` (600; каталоги700). Отправка `im.notify.system.add` отдельным серверным daemon не зависит от браузера и не занимает слот генерации. На одну версию один job, file lock + сохранённый статус + детерминированные TAG/CLIENT_ID. Готовый файл, частичная обработка и ошибка имеют разные сообщения, со ссылкой `/?portal=<id>&tab=tasks` (доступ проверяется обычным способом, ссылка задаёт первый экран один раз). Ошибка уведомления не меняет SEO-результат. Timeout после отправки — `uncertain`, падение после claim — `sending`; автоматически повторно не отправляются, чтобы не дублировать оповещение. Администратор видит счётчики таких доставок и ошибок. HTTP429/5xx: до3 попыток, Retry-After ограничен60с, transport timeout15с. Секреты/API bodies не используются в сообщениях ошибок. Официальные методы: [scope](https://apidocs.bitrix24.com/api-reference/common/system/scope.html), [im.notify.system.add](https://apidocs.bitrix24.com/api-reference/chats/notifications/im-notify-system-add.html).

Постоянный sender находится в уже включённом в Dockerfile `automatic_seo_host.py`; добавлять Python-файлы в образ не требуется. Ни schema migration, ни новые зависимости не добавлены. Живую генерацию нельзя прерывать выкладкой. Текущий запуск JEWEL v2 обслуживает отдельный локальный наблюдатель до установки новой версии; его состояние/результат — в WORK.md.
