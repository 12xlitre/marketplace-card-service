# Автоматическая оптимизация карточек

Первая версия автоматической оптимизации Ozon от 20 октября 2026 года. Аккаунт выбирает карточки, специалист запускает подготовку Excel, проверяет результат и принимает версию либо задаёт замечания для пересборки. После принятия специалистом файл передаётся аккаунту на согласование — пользователь подтвердил этот этап. Публикация остаётся отдельным действием. Поддерживается Ozon; расширение на WB отдельно.

Контрольный пример методики — редакция 3 Ideal Standard / AM.PM, получившая положительную оценку Насти. Текущий статус разработки и ссылки на файлы — в [WORK.md](../WORK.md). Методика источников, выбора ключей и проверки фактов — в [правилах массовой обработки](memory/product_mass_workflow.md).

## Создание задачи

В существующем окне «Взять в работу» появляется вариант «Автоматическая оптимизация». Аккаунт выбирает SKU, название задачи, специалиста в рамках существующего назначения, пункт отчётного периода и при необходимости комментарий/магазин конкурента. Порядок и состав карточек фиксируются при создании.

Внутренняя модель: задача «Контент» с `optimizationMode: automatic` в метаданных. Это отдельный вид работы в интерфейсе; он использует существующий маршрут согласования контента. Не требуется одновременно ставить отдельную задачу СЯ: получение необходимой семантики входит в подготовку файла. Ручная и автоматическая задачи могут существовать для одного SKU независимо. Предел автоматической пачки — 200 SKU, всего в кабинете — 500 задач; превышение не приводит к молчаливому усечению списка.

Рядом с каждым нашим товаром показано поле конкурента: специалист вставляет полный адрес карточки Ozon или SKU. Повторно вводить наш SKU и писать объяснение сопоставимости не требуется. SKU извлекается из ссылки на сервере без переходов по внешним адресам; принимаются только карточки домена Ozon. Для короткой ссылки нужен полный адрес открытой карточки. Назначения сохраняются между версиями; общий магазин не запускает универсальный автоматический подбор. Модель проверяет назначение, конструкцию, материал, монтаж/размер и комплектацию; явная несовместимость блокирует принятие. Отсутствие данных не считается совпадением.

## Задача специалиста

Внутри задачи: состав пачки, источники/дата данных, назначенные конкуренты, кнопка «Подготовить файл», прогресс по этапам и SKU. Для отсутствующих сопоставлений специалист назначает конкурентов до генерации соответствующих карточек.

Подготовка выполняется фоновой задачей сервера и продолжается после закрытия страницы. Повторное нажатие не создаёт параллельную копию той же работы. Одновременно выполняются до двух генераций на процесс сервера; при занятой ёмкости новый запуск отклоняется до обращения к API. Прогресс показывает подготовленные, требующие уточнения и неудавшиеся SKU; ошибочные повторяются без повторной генерации успешных. При частичной ошибке Excel не создаётся: интерфейс явно показывает это рядом с версией и объясняет ошибки. Номер попытки не означает наличие файла. Для готовой версии кнопка скачивания загружает Excel без перехода на страницу API; ошибки доступа/целостности показываются в задаче. После перезапуска сервера прерванный запуск можно продолжить с сохранённых результатов вручную.

После подготовки доступны:

- «Скачать файл» с номером версии и датой;
- «Принять файл» — принять проверенную версию и передать её аккаунту;
- «Пересобрать по замечанию» — указать область и запустить доработку;
- история файлов, замечаний и решений.

Принятие привязано к определённой версии файла, а не к последней версии по имени. При пересборке новая версия требует новой проверки. Неполный охват SKU, ошибка проверки книги или нерешённое противоречие, влияющее на предлагаемые факты, блокируют принятие соответствующего результата. Замечание к источнику, которое не мешает нейтральному подтверждённому тексту, можно оставить с явным решением специалиста и обоснованием.

## Замечания и повторная подготовка

Форма содержит SKU или «Вся пачка», раздел «Заголовок / Характеристики / Описание / Семантика / Конкурент», при необходимости ID характеристики и текст замечания с указанием подтверждения факта. Первая форма отправляет одно замечание за запуск; API поддерживает список до 100 замечаний. Внешние документы/фотографии как новые доказательства и импорт пометок из Excel не реализованы. Для смены конкурента редактируется сопоставление перед пересборкой. Произвольные изменения оформления Excel выполняются доработкой экспортёра, не интерпретируются из замечания к товару.

Пример: `5318018800 → Описание → не использовать спорную серию; остальные свойства сохранить`. Для фактического исправления цвета или гарантии нужен источник: свободный комментарий не становится автоматически достоверной характеристикой.

Пересборка повторно использует зафиксированные данные и анализ общего конкурента. Изменяет только затронутые SKU и разделы; заново проверяет связанные ключи, характеристики, счётчики и противоречия. Например, смена конкурента требует пересмотреть семантику и текстовые предложения данного SKU. Изменение общего правила затрагивает все SKU, к которым оно относится: область воздействия показывается перед запуском.

Незатронутые результаты сохраняются в новой версии. После замечаний аккаунта они возвращаются специалисту в ту же задачу и проходят этот же цикл. Предыдущие файлы и решения не перезаписываются. Уточнение конкретной карточки не меняет общую методику без явного отдельного решения.

Данные не обновляются молча между редакциями. Для обновления источников предусмотрено отдельное действие с датой и показом затронутых товаров; это может потребовать перепроверки ранее принятого текста.

## Excel для большой пачки

Количество листов не растёт с числом SKU. Первые пять сохраняются: «Итог», «Семантика», «Заголовки», «Характеристики», «Описания». Далее — источники и вопросы; короткая инструкция доступна отдельно. Не делать отдельный лист на каждый товар и не возвращать удалённые листы разбивки описания по абзацам/ключам.

| Лист | Организация просмотра |
| --- | --- |
| Итог | Одна компактная строка на SKU: артикул, товар, приоритет, число правок и вопросов, статус проверки. Ссылки на строки заголовка, характеристик, описания и вопросов. Фильтры и закреплённые идентификаторы. Длинные пояснения свёрнуты по умолчанию. |
| Заголовки | До/после рядом; полные добавления, удаления и обоснования сохранены. Фильтр по SKU. |
| Характеристики | По умолчанию фильтр показывает только предлагаемые правки. Все исходные корректные значения остаются в книге и доступны при снятии фильтра. |
| Описания | Полные тексты до/после рядом, новые ключи жирным. Без сокращения текста ради компактности; переход из «Итога» сразу к нужному SKU. |
| Семантика | Полный набор с решением, источником и подтверждением использования. Фильтры SKU, релевантности, назначения и решения. Число запросов не становится обязательным числом вставок. |
| Противоречия | SKU, поле, расхождение, действие/вопрос, источник. В рабочей версии приложения также решение и состояние вопроса. |
| Изменения версии | Для повторных генераций: SKU, поле, прежнее предложение, новое предложение, замечание и причина. Это сравнение версий, а не дополнительная разбивка описания. |

У книги — номер версии, дата данных, общий охват и число успешных/проблемных карточек. Подсчёт правок идёт по реальным отличиям: заголовок, каждое изменённое поле характеристики и описание; счётчики на главном листе сверяются с деталями. Поля API, дублирующие название и аннотацию, учитываются по одному разу в профильных разделах, а не повторно как дополнительные характеристики. Общие вопросы по источникам показываются отдельно от вопросов конкретных SKU. Исходный порядок SKU сохраняется; приоритет доступен как фильтр/сортировка, не как молчаливое изменение порядка.

Статусы и решения в приложении — источник согласования. Выпадающий список и комментарии в Excel допустимы как локальные пометки, но файл не должен обещать их автоматическую синхронизацию. Импорт отредактированного Excel в первую версию не входит; замечания специалист вводит через форму задачи.

Макет на пяти реальных SKU проверяет компоновку и сохранность содержимого принятого образца. Автотест экспорта проходит на 5, 50 и 200 искусственных SKU: охват/порядок, фиксированное число листов, текст и жирное выделение, безопасное сохранение строк и отсутствие выдуманных метрик. Это проверка экспортёра, не замер скорости всей генерации или оценка SEO сотен реальных товаров. Качество реальной генерации проверяется специалистом при запуске из приложения.

## Ресурсы и данные

Общие этапы выполняются один раз на запуск/источник: словарь категории, получение общей семантики и анализ одного и того же конкурента. Собственные факты и допустимость ключей проверяются отдельно по SKU. На доработке не отправляется вся история переписки и весь отчёт модели: только правила, затронутые факты, выбранный конкурент и конкретные замечания.

При разборе формулировок конкурента проверка допускает разницу регистра, пробелов и е/ё и сохраняет фактическое написание из источника. Цитата-подтверждение извлекается из самого описания. Не найденные в источнике кандидаты исключаются с явным замечанием; если ни одна предложенная формулировка не подтверждена, подготовка останавливается. Чужие свойства не переносятся автоматически.

Запуск сохраняет версию методики, снимки источников, выбранные сопоставления, результаты по SKU, замечания, файл и его хеш. Доступ к задаче, источникам и скачиванию проверяется по кабинету и текущему пользователю. Ключи кабинетов не входят в файл, запросы генерации или журналы. Принятие старой версии во время пересборки должно возвращать понятный конфликт версий.

## Код и эксплуатация

- `automatic_seo.py` — фоновая работа, сохранение версий, ограниченная пересборка, проверка текстовых вхождений, состояния и приёмка. Редактура выполняется моделью внутри структурированного ответа с исходным черновиком и финальным текстом; внешний хьюманизатор не подключён.
- `automatic_seo_host.py` — существующие права, собственные данные Seller API, версии/запросы MPStats и проверка значений по официальным словарям. До первого запуска проверяются подключения без сетевых запросов.
- `automatic_seo_xlsx.py` — Excel с навигацией, фильтрами, цветами, прежними значениями в комментариях, полными текстами и сравнением версий; после сохранения проверяются охват, счётчики, текст/жирный шрифт и отсутствие формул из внешних строк.
- `frontend/src/AutomaticSeoTask.jsx` — экран специалиста/аккаунта; ручные кнопки изменения статуса скрыты для автоматических задач. Назначенный `tech` готовит/принимает, назначенный `manager` согласует/возвращает; администратор может оба действия. Действующие ограничения доступа к Ozon сохраняются.
- `server.py` — маршруты, метка задачи и миграция уникальности `ozon_tasks`. Миграция сохраняет поля, ID, историю и счётчик ID; уникальность `(portal_id, task_id)` остаётся, прежний запрет нескольких задач на карточку снят. Повторный запуск миграции безопасен. Другие таблицы и ручные результаты не меняются.

Данные — в `<каталог SQLite>/automatic-seo/<portal_id>/<хеш batch_id>/`: `state.json` с источниками/результатами, компактный `metadata.json` для опроса прогресса и неизменяемые `seo-vN.xlsx`. Каталоги создаются с правами 700, файлы состояния/отчётов — 600; доступ идёт через проверяемый API. Файловые блокировки защищают состояние и повторный запуск. При опросе прогресса не загружается весь набор источников. Каталог входит в резервную копию `var` вместе с SQLite.

Удаление кабинета удаляет его каталог отчётов, включая источники и все версии. Воркер перепроверяет кабинет/задачу до сохранения; после удаления он не восстанавливает файлы. Это проверено тестом удаления во время незавершённой подготовки с сохранением данных другого кабинета. Срок хранения истории согласования требует отдельного решения; автоматическое удаление принятых версий не включено.

Автоматические задачи не восстанавливаются из localStorage. Устаревшее сохранение списка задач не может согласовать файл, сменить его режим/состав или восстановить ранее удалённую автоматическую задачу. Обновление источников — явная кнопка «Обновить источники и пересобрать всё»; она повторно обрабатывает всю пачку и создаёт следующую версию.

## API

Базовый путь: `/api/portals/{portal_id}/automatic-seo/{batch_id}`.

| Метод | Действие |
| --- | --- |
| GET | Версии, состояние/прогресс, вопросы, назначения конкурентов и доступные действия текущему пользователю. Сырые источники и ключи не возвращаются. |
| POST | `action`: `generate`, `revise`, `accept`, `approve`, `return`; `version` — ожидаемый номер, сначала 0. Несовпадение или повтор активного запуска — 409. |
| GET `.../file?version=N` | Конкретный проверенный Excel после проверки кабинета, состава задачи и хеша. Частичная/непроверенная версия недоступна. |

Для подготовки: `competitors: {"свой SKU": {"sku": "SKU или полный адрес карточки конкурента"}}`; необязательное поле `reason` сохраняет совместимость с прежними версиями; для доработки/возврата — `remarks: [{sku: "SKU или *", section, text, attributeId?}]`; для принятия вопросов к источникам — `acknowledgeIssues: true`. `refreshSources: true` на подготовке явно обновляет все источники. Принятие с блокирующими вопросами запрещено. Переходы: `running → review/partial/failed`, `review → submitted` специалистом, `submitted → approved/returned` аккаунтом; прерванный запуск определяется как `interrupted`.

## Формат ответа модели

Для автоматической оптимизации GigaChat получает две схемы данных: анализа конкурента и товарного результата. На действующем v1-адресе используется принудительный `function_call: {name: "prepare_seo_data"}` с единственной описанной функцией; читается объект `message.function_call.arguments`, а не свободный текст. Функция только описывает возвращаемые данные и не выполняет внешних действий. Контракт сверён с [официальной документацией GigaChat](https://developers.sber.ru/docs/ru/gigachat/guides/functions/generating-arguments-for-custom-functions). Обязательные поля/типы/перечисления передаются в API. Параметр response_format на фактическом окружении не обеспечил формат: это проверено живым запросом; поэтому одной инструкции «JSON» недостаточно. Прежние вызовы других функций приложения без схемы сохраняют свои параметры. Схема не заменяет проверку релевантности, фактов, словарей и полноты семантики.

Проверка релевантности разделена на порции до 32 запросов: каждая получает собственные факты товара и возвращает короткое решение по каждому запросу. Запросам назначаются идентификаторы q0/q1/…; каждый идентификатор — обязательное поле схемы, а текст запроса сопоставляется на сервере, исключая ошибки переписывания. Пропуски показываются конкретным списком. Это размер технического запроса, не квота добавляемых ключей. Проверенные порции сохраняются по хешу фактов/состава и используются повторно. Затем отдельный вызов готовит текст по конкурирующей структуре и компактной релевантной семантике. Фактическое размещение определяет приложение по точным вхождениям в итоговых полях и явно подтверждённым адаптациям; модель больше не возвращает огромную таблицу semanticDecisions вместе с текстом. Неразмещённые решения объединяются с полной оценкой релевантности, поэтому все исходные запросы остаются в Excel. Лимит времени проверяется между порциями, общий прогресс показывает их номера.

## Диагностика ошибок подготовки

Ошибки модели различают таймаут, сетевой сбой, HTTP-отказ, обрыв ответа по длине, некорректный JSON и неверную структуру. Для неподтверждённых фраз сохраняется конкретный список. Публичная ошибка содержит безопасный код, этап и контролируемые детали; тексты HTTP-ошибок и секреты не передаются. Журнал сервера фиксирует SKU, кабинет, версию, класс исключения и места вызовов без сообщений исключений, переменных и тел запросов/ответов. Ответы модели сохраняются только в приватном снимке задачи для воспроизведения, до проверки содержимого; metadata и скачиваемый файл не включают этот журнал. Общие проверки доступа и удаления кабинета сохраняются. Повторных вызовов модели по диагностике автоматически не выполняется.

## Подготовка к выкладке

Нужны зависимости из `requirements.txt`, включая `openpyxl>=3.1.5,<4`, и новая сборка `npm run frontend:build`. Серверный `/opt/opticards/Dockerfile` должен копировать `server.py`, `automatic_seo.py`, `automatic_seo_host.py`, `automatic_seo_xlsx.py`, `index.html`, `package.json`, `README.md`. [Точный патч](automatic-seo-runtime.patch) согласован пользователем 20.10.2026. Фактический статус выкладки и резервная копия записываются в `WORK.md`.

Рабочий порядок остаётся прежним: согласование изменения серверной обвязки, резервная копия SQLite/`var`, commit/push и штатный `opticards-deploy`. Перед выкладкой требуется проектный audit. Вручную редактировать код на сервере не нужно. Миграция схемы требует сохранить резервную копию перед первым запуском новой версии.

## Проверка интеграций

| Проверка | Результат и основание |
| --- | --- |
| Seller API: только чтение, таймауты/повторы | Используется существующий `ozon_request_json`: фиксированный host/allowlist, connect до 5 с, read до 15 с и общий deadline; до трёх попыток только при временной ошибке, с `Retry-After`. Добавлен только read-метод словарей. |
| MPStats: источник и повторы | Существующий GET-клиент с таймаутом connect+read 20 с, до трёх ограниченных повторов при временных ошибках; операции и SKU отмечаются в контексте кабинета. Пути версий/запросов сверены с [официальным API](https://mpstats.io/integrations/analytics-oz/). |
| Модель | Существующий клиент с таймаутом 45 с; для структурированной подготовки GigaChat — 120 с, для прежних вызовов GigaChat остаётся 60 с. Автоматических повторов генерации нет; успешные SKU повторно не оплачиваются при повторе ошибок. Не возвращённый/невалидный ответ не становится готовым файлом. |
| Изоляция и доступ | Проверки кабинета на каждом API и в воркере, проверка назначенных ролей, состава/версии и хеша; HTTP-тест другого кабинета, прав и обычного сохранения задач. |
| Секреты и ошибки | Ключи берутся из существующего защищённого хранилища; в модель передаются только товарные факты/семантика, в UI — безопасные коды/сообщения. Тест исключает утечку текста исключения. |
| Неполный результат и обратимость | Нет файла для приёмки при ошибках; сохраняются результаты для повтора. Все версии сохраняются, смена источников явная, маркетплейс не изменяется. |

Audit новой области: tenant SQL/файлы/скачивание, секреты и удаление при отключении — pass с проверками в `tests/test_automatic_seo_routes.py`; таймауты/повторы и отсутствие автоматической публикации — pass по используемым клиентам. Retention — warn: согласовать срок хранения истории отдельно, автоматическое удаление старых согласованных файлов не включено. Проверка ограничена новой областью приложения.

## Проверка решения перед реализацией

Premortem: возможные причины провала через 6–12 месяцев. Оценки проектные, не статистика; S — ущерб, O — вероятность, D — сложность обнаружения, каждая от 1 до 10. RPN = S × O × D. После мер пересчитывается ожидаемый риск.

| Сценарий | S/O/D → RPN | Мера | После меры |
| --- | --- | --- | --- |
| Несопоставимый конкурент приводит к неверным свойствам во всей пачке | 8/7/7 → 392 | Явные соответствия по SKU, проверка конструкции/комплектации, блокировка неподтверждённых свойств | 8/3/3 → 72 |
| Замечание к одному товару меняет ранее принятые тексты остальных | 8/6/7 → 336 | Фиксация источников/версий, область воздействия, сравнение версий и неизменность остальных результатов | 8/2/3 → 48 |
| Специалист принимает сотни SKU, не замечая неполный результат | 8/6/6 → 288 | Явный охват, статусы/вопросы, контроль полноты и принятие конкретной версии | 8/3/3 → 72 |
| Файл или источник другого кабинета доступен по ID | 10/4/7 → 280 | Проверка принадлежности задачи, запуска и файла на каждой операции, тест доступа другого кабинета | 10/1/3 → 30 |
| Свободное замечание превращается в неподтверждённый факт | 8/5/6 → 240 | Отделение пожелания к тексту от подтверждённого изменения свойства, проверка источника | 8/2/3 → 48 |
| Повторные клики/возвраты расходуют бюджет на всю пачку | 7/7/4 → 196 | Защита от дубликатов, кэш по источникам, пересборка только затронутого | 7/2/3 → 42 |
| Закрытие страницы обрывает работу; API-лимит оставляет скрытые пропуски | 7/6/4 → 168 | Фоновый запуск, сохранение прогресса, ограниченные повторы, явная частичная ошибка | 7/2/3 → 42 |
| Excel становится нечитаемым или теряет полный текст/жирные ключи | 6/6/4 → 144 | Общая навигация, фильтры, повторное открытие книги и проверка текста/форматирования | 6/2/3 → 36 |

Вердикт premortem: GO с условиями — область пересборки, версии, проверка полноты и изоляция файлов входят в первую реализацию.

Contrarian: сильнейшие возражения к сценарию:

- Удобная кнопка не делает автоматическим подбор прямого конкурента. Без достаточных данных нужен явный выбор специалиста; подмена сопоставления общей категорией неприемлема.
- Excel со ссылками ускоряет просмотр, но не гарантирует внимательную проверку 200 товаров. Приёмка должна явно показывать остаток непроверенных/проблемных результатов и не маскировать их общим зелёным статусом.
- Перегенерация по свободному тексту может давать бесконечные новые варианты без исправления причины. Нужны ограниченная область, источник факта и сравнение с предыдущим предложением.
- Открытый Excel не сообщает приложению, что специалист его прочитал или исправил. Нельзя автоматически принимать локальные отметки за решение в системе.
- Новый глобальный тип работ затронет много существующих правил завершения. В первой версии дешевле использовать режим задачи «Контент» с явной меткой «Автоматическая оптимизация» в интерфейсе.

Вердикт критика: начинать с Ozon, существующих пачек и файла для ручной проверки; не обещать публикацию, универсальный автоподбор или одинаково качественный результат во всех категориях. Расширение на WB требует проверки его источников, словарей и ограничений отдельно.

## Порядок внедрения

1. Режим задачи, экран специалиста, фоновый запуск и версия файла без изменения ручного процесса.
2. Перенос методики редакции 3 в сервис генерации с повторным использованием источников и новым экспортом Excel.
3. Замечания, ограниченная пересборка, сравнение версий, принятие специалистом и существующее согласование аккаунтом.
4. Проверка на пяти контрольных SKU и больших тестовых пачках; проверка сохранности ручных задач, отказов источников, версий, доступа и отсутствия автоматической публикации.

Готовность окружения и результаты выкладки записаны в `WORK.md`. Положительная оценка контрольного файла не заменяет содержательную проверку первого автоматически полученного отчёта.
