# Задачи, план и согласование контента WB/Ozon

Основание: сценарий Дмитрия от09.11.2026. Реализация: серверный процесс и рабочие экраны WB/Ozon добавлены09.11.2026;
результат проверок и production-ревизия фиксируются в WORK.md.
Прототип: `docs/prototypes/content-workflow.html`.

## Цепочка работы

Кабинет и контакты → период, карточки и план → фоновая подготовка СЯ →
подтверждение плана → календарь исполнителя → проверка СЯ → файл набора →
согласование СЯ → выбранные работы с контентом по тому же набору →
два отдельных клиентских файла → согласование → завершение.

Подготовка СЯ начинается **при создании периода** с работами раздела
«Карточки и контент», как поручил пользователь. Она не ждёт подтверждения плана;
проверка специалистом и клиентское согласование остаются отдельными этапами.
Автоматическое время ожидания MPStats/модели не занимает рабочие8 часов специалиста.

## Кабинет, контакты и план

- Аккаунт создаёт кабинет клиента, выбирает WB/Ozon и параметры подключения.
- Контактное лицо, email и телефон обязательны в новых формах создания кабинета
  и при создании плана. Старые кабинеты дополняются в форме периода. Для совместимости
  прежних интеграций API создания кабинета допускает отсутствие всего clientContact;
  переданный объект проверяется полностью. Новый план без контактов сервер не создаёт.
- При создании периода выбираются даты, пункты плана, **явный набор карточек**,
  исполнитель и предварительные сроки. Нельзя молча брать весь магазин вместо
  выбранного набора. Ручные пункты без карточек тоже сохраняются.
- План выгружается отдельным PDF. 09.11.2026 владелец передал
  `Honeybear_Ozon_план_работ_ноябрь_2026.pdf`: фирменные обложка/фото/логотип,
  цели, фактическая команда, работы с «Зачем нужно» и ответственными, контакты
  агентства. Название клиента для PDF и пояснения к работам редактируются в
  форме плана; клиент/команда/пояснения фиксируются в версии. Данные прежнего
  клиента и персонального менеджера из образца не копируются. Сохранённые
  PDF прежних версий остаются неизменными.
- Клиент согласует конкретную версию плана. Подтверждено Дмитрием09.11.2026:
  аккаунт нажимает «Клиент согласовал план», указывает дату/комментарий и обязательно
  прикладывает подтверждение. Решение без подтверждения не сохраняется.
- Хранить версию, кто/когда подготовил, выгрузил, отправил и подтвердил. Изменение
  согласованных объёма/сроков/работ создаёт новую редакцию, не переписывает историю.
  Выполнение задачи и подтверждение плана — разные состояния.
- «Работать / Создать задачу» открывается у пункта плана. Карточки, вид работы,
  назначение, плановая дата и связь с периодом переходят в задачу автоматически.
  Повторное нажатие открывает уже созданную задачу, а не создаёт дубликат.

## Календарь аккаунта и специалиста

Уточнение владельца09.11.2026 после выпуска календаря: **аккаунт назначает дни,
технический специалист оценивает время перетаскиванием**. После «Создать» или
сохранения новой версии плана автоматически открывается сквозной календарь
выбранного исполнителя на начало периода. Очередь фокусируется на задачах этого
плана, занятость других проектов остаётся видна; можно переключить очередь
на все проекты. Из сохранённого плана доступна «Распределить задачи по дням».

- Аккаунт перетаскивает работу на дату или нажимает «Назначить день». В форме
  есть только дата; минуты и начало не задаются. Дата хранится отдельно как
  day-assignment и отображается «Нужно оценить», не как фиктивные0/60мин.
- Специалист видит назначенные даты и задачи без оценки по всем проектам.
  Перетаскивает задачу в получасовую ячейку. Дата и начало берутся из точки;
  форма содержит только длительность. На телефоне — «Выбрать место» и нажать
  нужную получасовую ячейку. При переносе на другой день/час — тот же drag.
- Сервер определяет непрерывное свободное окно до следующего занятого интервала,
  границы видимой сетки и остатка480мин на день. Выбор длительности с шагом30мин:
  если окно30мин, только30мин; для прежних коротких окон менее30мин — их остаток.
  Сохраняются проверки пересечений и480мин под BEGIN IMMEDIATE на случай гонки.
- Только успешная оценка заменяет назначенный день реальным интервалом. Ошибка
  или отмена формы сохраняет день. До оценки нельзя подтвердить проверку работы.
- Если аккаунт назначает уже полностью оценённый480мин день, предлагаются
  свободные даты. Неоценённые задачи показываются отдельным счётчиком.
- Аккаунт двигает ещё не оценённые дни. Уже оценённый интервал переносит сам
  специалист; общий обзор руководителя не открывает новые права изменения.


Уточнено владельцем09.11.2026: отдельный раздел левого меню, без выбора кабинета.
Технический специалист открывает «Мой график» со своими задачами **по всем проектам**;
аккаунт и руководитель — «Календарь команды» с доступными специалистами.
Визуальный ориентир — календарь Б24, палитра остаётся OptiCards. Виды день/неделя
с часовыми интервалами и месяц с сеткой дат; стрелки, выбор даты и «Сегодня».
Очередь «Нужно назначить время» включает новые и прежние ручные/автоматические
WB/Ozon-задачи. Назначение дня, начала и длительности открывается прямо из графика,
из блока задачи можно перейти к исходной задаче. Перетаскивание предварительно
открывает форму подтверждения. Дубликат «Набор СЯ без периода» из шапки убран:
используется «Взять в работу» → «Не добавлять в план работ» → массовый запуск СЯ.


- Аккаунт раскладывает работы плана по дням всего периода. Специалист видит свои
  задачи на день и неделю по всем доступным клиентам, с переходом в задачу/набор.
- Специалист назначает длительность выполнения. Это оценка человеческой работы,
  а не длительность фонового запроса к модели. До оценки виден отдельный список
  «Нужно оценить», он не должен показываться как нулевая нагрузка.
- Время начала хранится в минутах от полуночи по МСК. Пересекающиеся
  интервалы одного исполнителя запрещены по всем проектам; соседние разрешены.
  Старые оценки без начала показываются отдельно и уже занимают дневной лимит.
- Максимум480 минут в день **суммарно по всем проектам одного специалиста**.
  Проверять на сервере в одной транзакции, включая конкурентные изменения аккаунта.
- При превышении показать занято/требуется/остаток и предложить следующий либо
  выбранный свободный рабочий день. Не переносить молча. Работу больше8 часов
  разбивать на дневные части с общей связью с задачей.
- Базовый график5/2, МСК,8ч. Администратор может менять рабочие дни недели
  каждого исполнителя. Исключения по конкретным датам (отпуска/праздники) пока
  не автоматизированы; нужны графики от владельца. Задачи вне диапазона периода требуют явного решения
  аккаунта о переносе/изменении периода; не теряются при поиске свободного дня.
- Представления: календарь по дням и карточки задач по состоянию. Ожидание клиента
  видно отдельным статусом и не блокирует новые8ч работы на каждый день ожидания.

## Массовое СЯ

- Период с выбранными работами по карточкам создаёт связанную задачу подготовки СЯ
  по выбранному набору и запускает её в фоне. Несколько контентных пунктов для
  одного набора не создают несколько одинаковых подборов.
- Без периода набор, взятый в работу на СЯ, имеет общую кнопку
  «Подобрать запросы по набору» — запуск по всем его карточкам.
- Использовать существующие постоянные задания, кеш решений и восстановление.
  Нынешний предел8 активных заданий на пользователя нельзя обойти созданием сотни:
  нужна постоянная очередь карточек набора, подающая их малыми порциями.
- Набор/период/исполнитель и карточка фиксируются сервером. Стартовые фразы
  определяются по каждой карточке. Неполные исходные данные дают понятный блокер
  отдельной карточки и не выдают весь набор как успешно завершённый.
- Нынешние задания доступны только пользователю-инициатору. Для нового процесса
  нужна проверяемая связь набора с аккаунтом и исполнителем: старт аккаунтом не
  должен скрыть результат от специалиста. Разрешение просмотра через задачу не
  раскрывает произвольные чужие задания. В истории различать инициатора,
  автоматическое сохранение и ручную проверку специалистом.
- В задаче видны готово/в обработке/ошибка по карточкам, общий прогресс, продолжение
  проблемных карточек и переход к конкретной карточке. Закрытие страницы не мешает.
- По завершении — уведомление Б24 **назначенному исполнителю** со ссылкой на задачу.
  Одна доставка на версию результата набора, отдельно успех/частичный сбой;
  не по одному сообщению на каждую карточку и не всем сотрудникам.
- Специалист открывает карточку, проверяет причины/запросы, добавляет/исключает,
  сохраняет итоговое СЯ. Автоматически сохранённый рабочий подбор не означает,
  что специалист утвердил его для клиента.
- Клиентский файл формируется **по составу задачи**, а не по всему кабинету.
  В нём используются итоговые снимки проверенных карточек. Нельзя включить
  непроверенные рабочие данные или бесшумно пропустить незавершённые карточки.
- На уровне задачи: «Клиент внёс правки» → загрузка/предпросмотр/применение файла
  по набору; либо «Принять без изменений» → подтверждение отправленной версии.
  Переименование файла не ломает сопоставление; чужие карточки/кабинеты запрещены.
  Несовпадение версии не должно затирать более свежую работу.

## Контент по согласованному СЯ

- Из пункта плана аккаунт создаёт работу по названиям, характеристикам и/или
  описаниям. Допускается выбрать только наименования без генерации остальных полей.
- Унаследовать тот же набор карточек и **согласованную версию СЯ**. Не собирать СЯ
  заново и не брать свежий несогласованный рабочий подбор вместо утверждённого.
- Общая кнопка «Переоптимизировать набор» запускает выбранные разделы по всем
  подходящим карточкам. Готовые/проблемные результаты видны отдельно; неудача
  одной карточки не скрывается под общим «готово».
- Для клиента ровно два вида файлов: **наименование + характеристики** в первом,
  **описания** во втором. В задаче только по заголовкам первый файл не должен
  создавать неподтверждённые изменения характеристик.
- Файлы имеют независимые версии/согласования. Принятие первого не означает
  принятия описаний. Задача завершена, когда приняты все требуемые ей результаты.
- Та же цепочка: проверка специалиста → передать аккаунту → скачать/отправить →
  клиентские правки или принять без изменений → выполнено / доработка.
- Принятие клиентом и перенос на маркетплейс — отдельные действия. Действующие
  правила ручной публикации WB и чтения Ozon сохраняются.

## Статусы и история

| Объект | Состояния и правило |
|---|---|
| План | Черновик → подготовлен к согласованию → отправлен → принят / нужны правки |
| Автоподбор набора | В очереди → собирается → готов / готов частично / ошибка / отменён |
| Задача СЯ | Подготовка → проверка специалистом → передано аккаунту → на согласовании клиента → принято / доработка |
| Задача контента | Ожидает согласованного СЯ → запланирована → в работе → проверка → передано аккаунту → на согласовании → выполнено / доработка |
| Файл | Сформирован → скачан аккаунтом / отправлен → принят / правки |

Статусы выводятся из фактов: создание/завершение заданий, сохранение итогов,
передача специалистом, загрузка правок, явное принятие. Человеческое решение
«проверил / клиент согласовал» всё равно требует явной кнопки; его нельзя вывести
из факта скачивания. Частичное завершение не завершает весь набор.

Сейчас связанный пункт СЯ считается выполненным после сохранения итогов карточек.
В новом процессе это ещё не клиентское принятие: нужна отдельная ступень
согласования. Старые завершённые периоды/задачи не пересчитывать задним числом;
новую цепочку включать явной версией процесса при создании новых задач.

Фиксировать дату, пользователя, задачу, версию и точный файл при скачивании
аккаунтом. Скачивание специалистом не является «аккаунт забрал».
Для письма сохранять получателя, вложения с версиями/хешами, тему, время,
инициатора и результат отправки. SMTP-принятие не означает прочтение клиентом
или согласование. Неизвестный исход отправки нельзя автоматически дублировать.

## Почта: что потребуется от владельца

- Почтовый сервис/домен, адрес и отображаемое имя отправителя.
- SMTP-сервер, порт и режим TLS/STARTTLS; логин.
- Пароль приложения либо другой способ авторизации — через защищённую настройку,
  без сохранения в документации/репозитории. Секрет сейчас не запрашивался.
- Reply-To, если ответы должны приходить на другой адрес; нужна ли копия аккаунту.
- Подпись/реквизиты и пример желаемого письма. Адрес клиента брать из контактов
  и показывать аккаунту вместе с вложениями перед отправкой.

Сначала письмо собирается как проверяемый черновик в задаче. Отправка только
после действия аккаунта; создание периода/подбора не отправляет письма клиенту.
Для окончательной настройки нужны сведения выбранного провайдера; способ
авторизации и ограничения будут сверены с его официальной документацией.

По поручению Дмитрия сведения не запрашиваются повторно сейчас: запрос образца
у Светы и получение почтовых настроек внесены в список дел в WORK.md.

## Рабочий контракт реализации

Основные экраны находятся в «Отчетный период» и «Задачи» обоих маркетплейсов.
По умолчанию план предлагает СЯ и комплексный контент: один общий файл
наименований/характеристик, другой — описаний. Можно выбрать отдельную работу.
Задачи создаются один раз вместе с планом; «Работать» запускает существующую задачу.
Старый редактор периодов без выбранного набора остаётся отдельным блоком.

- Новая редакция плана требует подтверждения заново. Предыдущие задачи архивируются,
  подтверждения/PDF/результаты сохраняются. Неизменившиеся карточки сохраняют
  готовое СЯ и оплаченный checkpoint задания MPStats. Неизвестное создание отчёта
  не обходится ни retry, ни правкой плана. Подходящие записи календаря переносятся;
  остальные явно освобождаются с записью количества в истории. У периода также
  доступен прежний итоговый XLSX-отчёт после окончания дат.
- Сервер резервирует1..480мин на дату с `BEGIN IMMEDIATE`, учитывает все кабинеты
  исполнителя, предлагает3 следующих подходящих рабочих дня в пределах периода.
  Перед человеческой проверкой карточек нужна оценка длительности. Фоновая модель
  запускается независимо от этой оценки. Большую работу распределяют по датам.
- Постоянная очередь набора подаёт карточки в существующую очередь8/user,64global.
  Job и его связь с карточкой набора фиксируются одной транзакцией. Перезапуск
  сервиса не запускает прежние периоды; работает только новая явно созданная очередь.
- Финал специалиста фиксируется в задаче отдельным действием после сохранения итога
  в карточке. Автосохранённый подбор не считается финалом. На WB сохраняются частоты
  WB/Ozon и обоснования; Ozon сохраняет требование прямой частоты Ozon.
- Контент привязан к ID неизменяемого согласованного файла СЯ. Retry сохраняет этот
  ID; новые несогласованные рабочие запросы в генерацию не подмешиваются. Отдельная
  кнопка «Переоптимизировать набор · новая версия» явно создаёт следующую генерацию.
- В задаче два независимых вида контентных файлов. Возвращённые файлы сливаются
  только по своему разделу. Правка наименования не перезаписывает описание, а принятие
  неизменённого описания переносится в следующую версию при доработке наименования.
- XLSX содержит скрытый manifest: задача, файл, поколение, версия и листы/карточки.
  В СЯ редактируются решения G/J «Да/Нет», в контенте E/F (значение/решение).
  Перед применением сервер показывает preview с hash исходных байтов. Чужие,
  устаревшие файлы, изменённые защищённые столбцы и формулы отклоняются. Точные
  возвращённые байты, hash и автор сохраняются отдельно от нового рабочего XLSX.
- Файл, выгрузка аккаунтом, отправка письма, клиентское принятие — отдельные события.
  SMTP acceptance означает принятие сервером почты, не прочтение и не согласование.
  После сетевого обрыва или рестарта при отправке — `uncertain`, автоматического
  повтора нет. Повтор того же requestId и письма не создаёт второй outbox.
- Настройки SMTP доступны только `user_role=admin`, секрет зашифрован штатным
  хранилищем service integrations. Отправка только по явной кнопке аккаунта.
  Поддерживаются SMTP SSL/TLS и STARTTLS с логином/паролем приложения, без OAuth.
- Б24 использует проверенный webhook штатного модуля уведомлений и соответствие
  login→USER_ID. Только известная `anastasia.tech` получает исходное91; для других
  нужны реальные ID. Без настройки уведомление `blocked`; администратор может
  повторить только заведомо не отправленные, заблокированные уведомления.

### API и права

`GET/POST /api/content-workflow`, приватные `/calendar`, `/file`, `/proof`, `/settings`.
Действия: `create_plan`, `revise_plan`, `approve_plan`, `standalone`, `content_task`,
`schedule`, `unschedule`, `calendar_schedule`, `calendar_unschedule`, `calendar_assign_day`, `calendar_unassign_day`, `start`, `cancel`, `regenerate`, `review_card`, `export_files`,
`export_plan`, `mail_draft`, `send_mail`, `approve_file`, `import_preview`, `import_apply`.

Аккаунт — проектная роль manager либо настоящий admin; глобальный обзор руководителя
сам по себе не даёт права принять клиентский файл/план или настроить почту.
Специалист — назначенный исполнитель с актуальным доступом; видит прогресс заданий
аккаунта через задачу, без расширения доступа к произвольным чужим semantic-jobs.
Техспециалист с назначенной незакрытой задачей получает право локального редактирования
Ozon-СЯ/контента; credentials, состав кабинета и прежние read-only задачи этим не открываются.
Все операции проверяют кабинет, роль, текущую версию/поколение. Скачать архивный файл
можно по прежним правам, согласовать его заново нельзя. Старый API изменения плана
не обходит версионирование новых периодов. POST проверяет Origin при наличии и
ограничен120 запросами/мин на пользователя в процессе; очередь и480мин — в SQLite.

`GET /api/content-workflow/calendar?start=YYYY-MM-DD&end=YYYY-MM-DD&assignee=all|login`
не требует portal_id; максимум94 календарных дня. По умолчанию техспециалист
получает только себя, аккаунт/руководитель — all по своим разрешениям. Ответ:
login/canManage/people(login,name,weekdays)/tasks(id,source,portalId,project,
marketplace,assignee,canEdit,closed,groupKey,schedule)/days(assignee,day,used,tasks),
limit480, timezone. Чужая занятость общего специалиста учитывается агрегатом,
названия и задачи чужих кабинетов не раскрываются. Просмотр readonly: не создаёт
новые задачи и не вызывает провайдеров. Активность текущего пользователя и
актуальный доступ к проектам перечитываются из БД.

`calendar_schedule` принимает portalId/taskId/day/minutes/startTime(HH:MM)/moveFrom;
`calendar_unschedule` — portalId/taskId/scheduleId. Для новых задач работает прежняя
проверка текущей версии; для legacy сервер заново находит исходную активную пачку,
проверяет исполнителя/аккаунта и project scope. Расписание старых задач живёт в
workflow_legacy_schedule, без запуска worker. Оба источника участвуют в одном
серверном лимите и проверке пересечений под BEGIN IMMEDIATE. Переполнение409
workflow_day_overloaded; пересечение409 workflow_time_overlap, предложения трёх
рабочих дат без автоматического переноса. Скрытая занятость не раскрывает названия.
При массовом СЯ с legacyGroupKey слот переносится в новую workflow-задачу,
источник исключается из очереди; повторный requestId не дублирует работу/часы.
Удалённую/завершённую legacy-задачу с оценкой можно снять с календаря, сохранив
доступ только назначенному специалисту/аккаунту/администратору.

Frontend: `/?screen=calendar`, `/?screen=guide#guide-calendar`; полная инструкция
«Как работать» покрывает контакты/план/PDF/календарь/СЯ/контент/файлы/SMTP/Б24.
Переход legacy-задачи использует portal/tab=tasks и hash calendar-task-<groupKey>.

`calendar_assign_day` принимает portalId/taskId/day и необязательный assignmentId
для переноса конкретной даты. Только manager этого проекта либо admin. Идемпотентно
по task/day; проверяет активную задачу, актуальную версию, рабочие дни и границы
периода. `calendar_unassign_day` принимает taskId/assignmentId и снимает только
день, не реальные оценки. `task_day_assigned/task_day_removed` входят в историю.

`GET /api/content-workflow/calendar-window?portal_id=...&taskId=...&day=...&startTime=HH:MM&windowEnd=1080`
возвращает startMinute/endMinute/maxMinutes/used/limit для выбранного места, без
названий чужих работ. windowEnd — нижняя граница видимой часовой сетки в минутах
от полуночи, по умолчанию18:00; допустимо1..1440. При `calendar_schedule` тот же
windowEnd не позволяет выйти за выбранную сетку; overlap/480 проверяются заново
в транзакции. API старых оценок без windowEnd остаётся совместимой.

Calendar task дополнен periodId/planTitle/periodStart/periodEnd; schedule содержит
как реальные оценки, так и plannedOnly=true с minutes=null/startMinute=null.
День содержит unestimated — число назначений без оценки. Batch detail содержит
plannedDays. Назначения не участвуют в SUM(minutes), но явно видны в интерфейсе.
Подходящие дни переносятся на новую версию плана; остальные освобождаются.
Отмена/завершение/удаление новой задачи снимает pending-дни; неактивные legacy-группы не показываются, их данные удаляются каскадно с кабинетом. Массовый старт legacy СЯ
переносит их на связанную workflow-задачу вместе с прежними оценками.

Deep-link после сохранения: `/?screen=calendar&calendarAssignee=<login>&calendarPeriod=<id>&calendarDate=YYYY-MM-DD`.
Фильтр очереди не ограничивает сетку видимых проектов назначенного специалиста.
«Как работать» дополнена сценариями Света→дни / Настя→drag / окно30мин.

### Хранилище и эксплуатация

Новые таблицы: workflow_plans, workflow_plan_versions, workflow_batches,
workflow_cards, workflow_files, workflow_returns, workflow_events, workflow_schedule,
workflow_people, workflow_outbox, workflow_legacy_schedule, workflow_day_assignments.
Последняя хранит только даты и FK/cascade к кабинету, исполнителю, batch для новых
задач; task_id также поддерживает прежние WB/Ozon-группы. В обеих таблицах
расписания добавлен nullable start_minute (0..1439); прежние даты/минуты не меняются.
У portal_work_periods добавлен workflow_version=2;
старые записи0. Все данные кабинета связаны FK/cascade; SMTP — общая админская
интеграция. BLOB файлов и подтверждения входят в консистентную SQLite backup.
История не очищается автоматически: удаляется каскадно с кабинетом.

Одновременно работает один лидер workflow на БД (flock). При аварии в момент
незафиксированного ответа контентной модели возможен повтор одного вызова; готовые
карточки не повторяются. Исходящие `sending` после рестарта помечаются `uncertain`.
WAL и схема запуска существующей очереди не менялись. Инициализация существующей
схемы не выполняет пустые записи при каждом чтении, чтобы избежать вложенной
блокировки SQLite. Новая Python-логика находится в server.py, который уже входит
в production-образ; зависимости добавлены в requirements.txt, JSX собирается в index.html.

Фирменный образец PDF получен и применён. Для отправки достаточно SMTP с
логином/паролем и защищённым TLS; IMAP нужен для отдельного будущего приёма ответов.
Реквизиты реальной почты и проверка доставки пока ожидаются от владельца.
Тестовые SMTP/Б24/модель в локальной приёмке подменяются на границе транспорта,
письма реальным клиентам и оплаченные генерации для тестов не запускаются.

[Python smtplib](https://docs.python.org/3/library/smtplib.html),
